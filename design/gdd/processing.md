## Summary

18 是**把原料变成药的地方**。它是全案「**转化是有代价**」(⚠️ 21a 的锚点三,非 game-concept 支柱三 —— BL-7 订正,见页眉)最直接的手艺载体。

**18 的核心纪律是「不发明结算」。**

> `item-database.md:450` 逐字写:**「17 采集 / 18 炮制 / 19 制作只产出输入参数,不得自建结算逻辑」**。

**F1 是唯一的配方求解器**(`item-database.md:461`),它**住在 21a**。18 的职责是**四件事**:

1. **筛出炮制子集** —— `Recipe` 全集中哪些属于「炮制」(不是制作 / 不是建造);
2. **供四个修正项**的**输入等级** —— `SkillMod` 传**等级**(不是结果)、`QualityMod` 传**输入实例**、
   `EquipMod` 读 24、`EnvMod` 读 5;
3. **调用 F1** —— **一次**,得 `ActualConsumed` / `OutputQty` / `OutputQuality`;
4. **交 20 执行装卸** —— 18 **不碰库存**,它把「要消耗什么、要产出什么」交给 20。

> **⚠️ 18 的判据**:18 的代码路径里**不得出现** `Ceil(base / EFF)` / `Round(qty × QtyMultiplier)` /
> `clamp(InputQuality × Retain, 1, InputQuality)` 的**求值** —— 它们是 **F1 / F2 的正文**(住 21a)。
> 由 **AC-18-02** 的**单调用点**断言守。

## Overview

**18 是「手艺」而非「配方表」。** 配方表是数据(21a);18 是**执行它的那双手**。

**18 的三个面**:

| 面 | 内容 |
| --- | --- |
| **准入** | `skill_gate` / `min_quality` —— 「这个方子你够不够格做」「这料配不配用」 |
| **时序** | `duration_ticks` —— 炮制**要时间**(玩家在等,病人在等) |
| **结算** | **调 F1**(唯一求解器)+ 交 20 装卸 |

**18 与 20 的边界**(承 20 规则五):**18 算出量,20 搬运**。18 **不持有库存**。

> **⚠️ 18 是「看不见的手艺」的载体** —— 它的反馈**不在面板上**,在**成药的品级**
> (21a 的 `drug_quality_character[]`,呈现在药签措辞 / 质地上)。
> **18 永不显示「转化率 85%」这类数字**(反幻想)。

## Player Fantasy

**「火候差一点,赔的是料,赔的是色。」**

> **⚠️ 2026-09-19 首轮评审 BL-3 订正**:原头句作「火候差一点,**药就废了**」,与同文规则六 /
> `AC-18-07`(产出**结构上 ≥ 1**;该条已于同日 AC 全表改造中并入 `AC-18-01` ②)、21a `:731`(「不归零、没有全废」)、边例「技能为 0 也**不失败**」
> **同节自相矛盾** —— 「废」这个结局在 18 的规则里不存在。改述为实际交付的幻想:**烧料 + 赔色**。

- **手艺有代价** —— 同样的原料,手艺好的人**省料**(`ActualConsumed` 贴近基数),
  手艺差的人**烧料**(实耗翻倍)。**这个差别是渐进的,不是「成功 / 失败」**。
- **永远提不上去,只能保得住** —— **炮制不能把次料变成好料**(21a F2 的 `clamp` 上界 =
  `InputQuality`)。**你只能尽量不损失**。**采集的白给感由此被堵死**(承 21a F2 的 🔑)。
- **等待是真实的** —— 炮制**要时间**。这段时间里,病人还在病着(支柱二)。
  **制一剂药不是瞬发动作,是一段等待。**

### 具名机制:点火时机的选择(R-18-A,2026-09-19 新增 · BL-3)

> **本系统是 18 唯一的玩家判断面,原稿从未给它名字。**

`EnvMod_raw` 是块哈希阶梯量(5 的 R-5-A):**块与块之间跳变、块内恒定**;`OQ-18-6` 已裁
「**点火那一 tick 取即时值、无历史无累积**」。⇒ 玩家在手艺轴上的能动性**不是**「盯着火调」
(那个量在机制上不存在,见 Game Feel 的 BL-3 订正),**而是「选在哪一 tick 点火」** ——
同一个方子,**赶在下一场雨之前起炉** vs **冒雨起炉**,`QtyMultiplier` 与实耗不同。

| 项 | 口径 |
| --- | --- |
| **判据** | `EnvMod_raw(cell, start_tick)` 随 `start_tick` 变化 ⇒ 点火时点是**有代价的选择** |
| **可见性** | 玩家可读的是**在场观察**(天光 / 雨 / 风,经 42/44)+ **史实经验**(晒不干、灶前背光);**禁**读数值(**`skylight` 仅呈现,永不进判定**,承 `time-and-weather.md` 的 OQ-5-7 口径) |
| **不可行面** | 玩家**无法**「等火候变好再收」—— 结算是**点火的一次性纯函数**(规则八),不存在中途修正 |
| **支柱归属** | **支柱一**(判断为骨)在制程侧的落点;与「等待可读性」(`AC-18-21`)配对成立 |

> **⚠️ 升格不扩范围**:无新数据字段、无新 `Kind`、无新公式 —— 只是把**已经存在的判断**写出来。
> **⚠️ 它也不改变「起炉/取药 ≤ 1 帧」的预算**:该预算是**操作响应**,不是**判断深度**。

> **⚠️ 18 的幻想有硬边界:它不能变成「合成菜单」。**
> 无「配方解锁列表」、无「可制作 / 不可制作」的灰置网格、
> 无「成功率 90%」的骰子。**手艺是一个持续的量,不是一次抽签**(承 21a 的 `EFF` 曲线)。
> ⚠️ **2026-09-19 BL-8 注**:**「灰置提示禁」≠「配方不存在于世界」** —— 后者会顺手封死成长目标
> (见规则十「配方可知性」与 `AC-18-20`)。**反幻想禁的是面板,不是史实内的线索。**

## Detailed Rules

### 规则一:18 不发明结算 —— F1 是唯一求解器(住 21a)

**承 `item-database.md:450`**,18 是**调用方**,不是求解方:

| 项 | 归属 | 说明 |
| --- | --- | --- |
| **F1 的正文**(`OutputQty` / `ActualConsumed` / 守恒律) | **21a** | 唯一出处(`:461-555`) |
| **F2 的正文**(`OutputQuality` / `Retain` / `EFF`) | **21a** | 唯一出处(`:552-593`) |
| **F1 的代码实现**(单调用点) | **共享求解器** | 18 是 **P0 唯一调用方**(19 制作是 P1a) |
| **四个修正项的「等级 / 实例」输入** | **18** | 18 供料,**21a 定曲线** |

> **⚠️ 关键分工(承 21a F1 的 🔑)**:`SkillMod = cap × Level / SKILL_CAP` ——
> **「18 只传等级,不传结果」(修正曲线由 21 定义)**。
> 若 18 自己乘了 `cap`,曲线会**死亡**(在 `int` 域预先除尽 ⇒ 两段阶跃)。
> **由 AC-18-03 守。**

### 规则二:炮制子集 —— 从 `Recipe` 全集中筛

**21a 的 `Recipe` 表是一张,不属于任何单一系统。** 18 消费其中的**炮制子集**:

| 子集 | 归属 | 判据(**2026-09-19 R-18-B 后 = 唯一互斥判据**) |
| --- | --- | --- |
| **炮制**(加工状态链) | **18** | `Recipe.owner = process` |
| **制作与器械**(成品 → 器具) | **19**(P1a) | `Recipe.owner = craft` |
| **建造**(→ `build_part`) | **23** | `Recipe.owner = build` |

> **🔴 R-18-B(2026-09-19 首轮评审 BL-5 · 结清 `OQ-18-1`,用户裁定 [甲])**:
> 原稿的三条判据(`processing_state` 变化 / `category = tool` / `category = build_part`)
> **结构上不互斥** —— `item_key = (base_id, processing_state)`(21a 规则二 D-21-2)使
> `tool` / `build_part` **天然带 `processing_state`**,任何「材料 → 器械/建材」且 state 变化的配方
> **同时命中 18 与 19/23** ⇒ 双落流点、双 `Craft` 发起方。
> 且 21a `:416-423` 的转化归属表是**逐转化**的,18 的判据是**逐配方**的,**层级不同且从未调和**。
>
> **裁决:「子集归属」升级为 `Recipe` 的显式数据字段** `owner ∈ {process, craft, build}`,
> **住 21a 的表**(18 不自己加字段 —— 承 21a 的「一处声明」纪律)。
> ⇒ **回 21a 的登记义务 `O-18-R1`**(`Recipe` 结构 + 烘焙期枚举闭合校验 + 逐配方与转化表一致性检查)。
> **18 侧的判据就此从「约定」升为「字段」**:准入前置 `owner = process`。
>
> **原 `processing_state` 变化判据降为校验而非归属**:烘焙期断言
> `owner = process ⇒ ∃ i, j: outputs_i.state ≠ inputs_j.state`(**方向单向** ——
> `owner = craft/build` 的配方**允许**改变 state,那不再使它归 18)。
> **不交并覆盖由 `AC-18-18` 守**(判据改为字段后,夹具可测)。

**P0 的加工状态链**(承 `item-database.md:418-423`):

```
raw ──干燥──▶ dried ──提取──▶ extracted ──成型──▶ pill
                  └──浸制──▶ tincture
*(P1a)* raw ──蜜炙──▶ honey_fried ; raw ──清炒──▶ dry_fried
```

> **🔴 链深口径订正(2026-09-19 BL-4)**:原稿写「`raw → pill` 是**两步**、P0 应保证**链深 ≤ 2**」,
> 但按上图与 21a `:418-423`,同一株料从 `raw` 到 `pill` = **干燥 + 提取 + 成型 = 3 次转化、3 条 `Craft` 事件**;
> 边例表亦曾重复「两次」之误。现**定义并更正**:
>
> - **`链深` := 一条链上的**转化次数**(= `Craft` 事件条数),不是中间态数。**`raw` 自身的深度 = 0**。
> - **P0 约束 = 单条配方恒为 1 次转化**(一炉 = 一条 `Craft`;`raw → pill` **不是**一条配方)。
>   上表的三段各自是一条配方 ⇒ 全链深度 3 是**内容**属性,不是**单炉**属性。
> - **`P0_MAX_CHAIN_DEPTH`(链深上限)归内容轮裁**(原 `OQ-18-4` 的一半);其**时间预算论证**
>   (`链深 × duration_ticks` ≤ 一次出诊的可用 tick)现**挂 `OQ-25-8`**(tick 频率无值 ⇒
>   出诊预算无量纲),**登记 `BLOCKED-BY`,不得由 18 自填 tick 频率**。

### 规则三:准入两道门 —— `skill_gate` 与 `min_quality`

**承 21a 的两条字段**(`:163` / `:165`),18 是**执行方**:

| 门 | 判据 | 性质 |
| --- | --- | --- |
| **`skill_gate`** | `QueryLevel(玩家, CRAFT_SKILL) ≥ Recipe.skill_gate` | **门槛,不是系数**(21a `:163` 明文) |
| **`min_quality`** | `min(输入实例的 quality) ≥ Recipe.min_quality` | **准入闸**(「这方子只收好料」) |

> **⚠️ `min_quality` 只做准入,不改药效**(21a `:167` 明文)——
> **品级的出口只有 F5 的时间轴偏移**(21a `:658-669`),不是「好料 = 更猛」。
> **判据**:18 **不得**读 `min_quality` 去调制任何幅值(`AC-18-05`)。
>
> **🔴 裁决权威 = 主机终裁(2026-09-19 BL-5/I-1 补,承 ADR-011 Amendment B 口径)**:
> 两道门的**判定谓词住在 18 的 sim 侧、在主机 `Step` 内求值** ⇒ 结论逐位可重放。
> 客户端在同一 tick 上**预答同一谓词**,但其作用**只是呈现门**(决定「这方子在我眼前出不出现」),
> **永不进入结算**;客户端预答与主机终裁不一致时,**以主机为准、本地零副作用**
> (与 10 的「本地判定降级为预表现」同构 —— **不是新机制,是同一机制的第二处应用**)。

### 规则四:四个修正项的输入侧 —— 18 供料,21 定曲线

**承 21a F1 的变量表**(`:478-486`):

| 项 | 21a 的曲线 | **18 供什么** | 供料的源系统 |
| --- | --- | --- | --- |
| `SkillMod` | `cap × Level / SKILL_CAP` | **`Level`(整数)** | **30**(`QueryLevel`) |
| `QualityMod` | `cap × (InQ − 1) / (MAX_QUALITY − 1)` | **输入实例集**(`InQ = min(quality of 被点名的实例)`) | **20**(实例集) |
| `EquipMod` | `cap` | **`EquipMod` 的值** | **24**(医馆器具档位) |
| `EnvMod` | **两个未钳制分量原样透传** | **`EnvMod_climate`(= 5 的 `EnvMod_raw`)+ `EnvMod_clinic`(= 24 的医馆分量)** | **5** + **24**(分别供,**18 不相加、不钳制**) |

> **⚠️ `EnvMod` 可为负** —— 它是**唯一**允许负值的修正项(21a `:485`「火候难控、背阴」)。
> **18 必须原样传递负值**,不得 clamp 到 0(`AC-18-06`)。
>
> **🔴 R-18-C(2026-09-19 首轮评审 BL-9 · 结清钳制归属)**:原稿三处口径互相指认、**无人执行钳制** ——
> 5 的 `:395` 写「唯一钳制点 = **21a**」(且 `time-and-weather.md` 的 `AC-5-19` 断的是**别人**的行为);
> 18 原 `F-18.1` 把 `EnvMod` 的源写成「5 + 24」合并后交(= 18 合);
> 21a `:484` 的变量表把 `[ENV_MOD_MIN, ENV_MOD_MAX]` 写成**入参断言而非被执行的操作**,F1 正文只 clamp **求和后的 `ΣM`**。
> 后果(静默):若无人钳制,则 21a `:533` 的构建期不等式**保护的是一个不存在的包络**,
> `AC-18-14` 通过仍挡不住「高投入段被 `clamp` 静默截断」。
>
> **裁决(形状归本件,执行方归 21a)**:
> 1. **18 只透传两个未钳制分量**(上表),**不相加、不钳制**(与 5 的 B-3「5 侧不钳制」同构);
> 2. **求和 + 钳制的唯一落点 = 21a `F1` 正文**,新增具名式(归 21a 撰写,**义务 `O-18-R2`**):
>    `EnvMod_total = clamp(EnvMod_climate + EnvMod_clinic, ENV_MOD_MIN, ENV_MOD_MAX)`
>    —— **且该式的执行方须有一条 21a 侧 AC**(21a 现无 ⇒ 该 AC 不得由 18 代持);
> 3. **5 的 `AC-5-19` 收窄为只断言自家不钳制**(不得在 5 的文档里断 21a 的行为 = 借来的绿)。
>
> **⇒ 18 侧的可验面因此收窄**:`AC-18-06`(原样传负值)成立;原 `AC-18-14` 的**构建期执行方错配**
> 一并订正 —— **构建期四 cap ↔ `QTY_MULT_MAX` 校验不跑 18 的代码**,主执行方 = **21a 的烘焙管线**
> (ADR-014 阶段 2;21a 已有 `AC-21a-3/9` + 负向夹具)。18 侧至多留一条**装载期防御断言**
> (`AC-18-14` 就此改判,见 AC 表)。**`OQ-18-2` 随本条结清。**
>
> ⚠️ **同链的真缺陷(不在 18 修,归 21a)**:systems-designer 复核证明 21a `:511` 的构建期
> **聚合式**可被运行期的**逐条 `Round` 上取整**击穿(反例:`base 重量积 = 100`、`EFF_MAX = 1`、
> `QTY_MULT_MAX = 1.5`、单条 `qty = 1` ⇒ 构建期 `99 ≤ 100` ✓,运行期 `Round(1.5) = 2` ⇒ `132 > 100`,
> **凭空 32%**)。缝在 `Round` 不在 `max(1,·)`(后者可证安全)。修复 = 构建式改**逐条同形极值式**,
> **登记义务 `O-18-R3` 归 21a**;18 的边例「守恒律被击穿 = 不可达」在 21a 修复前**不得记绿**
> (见 Edge Cases 与 `AC-18-19`)。

### 规则五:调用 F1 —— 一次,且拿三个出参

```

### 规则六:产出非零是结构,不是承诺(承 21a `max(1,·)`)

### 规则七:与 20 的原子性(承 20 规则六)

**18 算出量,20 执行装卸;装卸是原子的。**

```
18.Process(recipe, 输入实例集):
    ① 准入两门(规则三)+ 子集字段 owner=process(规则二) —— 失败 ⇒ 不进入
    ② 单炉占用检查(规则八) —— 该玩家已有进行中的炉 ⇒ 拒绝,零事件

> **⚠️ 容量不足时(点火时点)**:20 整体拒绝 ⇒ **18 的炮制不发生**(原料不扣、药不出、**`Craft` 事件不落流**)。

>

> **世界流里不得存在指向不存在的炉子的事件** —— 事件落流即代表「这一炉已进入时间轴」,
> 因此 20 的容量裁决必须**先于** `Append`(`AC-18-16`)。

### F-18.2 · 准入(两道门,整数比较)

```
Admissible(recipe, player, consumedInstances) ⟺
      QueryLevel(player, CRAFT_SKILL) ≥ recipe.skill_gate
    ∧ min(quality of consumedInstances) ≥ recipe.min_quality
```

| 门 | 类型 | 改坏的后果 |
| --- | --- | --- |
| `skill_gate` | **门槛**(非系数) | 若当成系数 ⇒ 与 `SkillMod` **双重计数**(曲线被算两遍) |
| `min_quality` | **准入闸** | 若当成药效调节 ⇒ 违反 21a `:167`(品级出口只有 F5) |

> **⚠️ BL-9 补注(2026-09-19)**:
> ① `min(quality of consumedInstances)` —— 求 min 的对象是**被点名的实例集**,不是
> `inputs[]` 行(20 规则六允许跨栈凑量点名,行级 min 会静默放行「凑出来的差料」)。
> ② **裁决权威 = 主机终裁**(R-18-A / ADR-011 Amendment B 同构):客户端可跑同一谓词作
> **预答**(只决定面板显隐,是**呈现门**);**`Admissible` 的权威求值发生在主机收到意图
> 的那一 tick**,拒绝 = 零事件落流。客户端预答与主机终裁的口径必须同源(同一份谓词实现),
> 禁两份实现。

### F-18.3 · 完成时点(tick 计)

```
CompleteTick(craft) = craft.start_tick + recipe.duration_ticks
```

> **⚠️ 纯 tick 算术**,无墙钟、无浮点。**`duration_ticks` 值归用户**(§Tuning Knobs)。
> **BLOCKED-BY-OQ-25-8**(tick 频率无值):`duration_ticks` 的**秒级意义**在 tick 频率标定前
> 不可判读 —— 出诊时间预算(规则二)同押此值。公式本身不受影响(纯整数加法)。

## Visual/Audio Requirements

### 视觉(承 42)

- **视觉 = 炮制的过程**:
  - **火候 / 水汽 / 研磨的工具动作** —— 世界内的**手工**,不是进度条;
  - **等待的可见性**:炉子在那儿烧着,你走开它还在烧 —— 这是**器物状态即进度**的视觉侧
    (承 42 `:1124` 已裁口径:不发生在纸上的进程,42 不画进度条,进度住世界器物);
  - **成品的质地** —— 承 21a 的 `drug_quality_character[]`,以**药签措辞 / 外观**呈现;
  - **溢出起货的可见性**(R-18-D):「药滚了一地」是**世界内事件**,不是弹窗 —— 落地物走 20 的正常拾取呈现。
- **一律无数字**:无转化率 / 无成功率 / 无进度百分比。

### 音频(承 ADR-018 · BL-10 改判:18 = cue 发射方)

> **⚠️ 本轮改判**:44 `:697` 把 `sfx_decoct_*` 的发射方记在 **23/24** 名下 —— 错。
> 起炉 / 起货两个时点由 **18 的调度产生**(23 动画、24 机器都不持有「点火/起货」这一 tick 事件),
> **发射方 = 18**。涟漪:44 侧回写发射方 + 上游表补 18 行。

- **cue 命名**:仓库规约 `sfx_[system]_[event]` ⇒ **`sfx_process_light`**(起炉)/
  **`sfx_process_complete`**(起货)/ 行为声床 `sfx_process_work`(捣药 / 翻炒 / 注水,随动画节拍);
  44 既登记的 `sfx_decoct_*` 系列**并入本命名族或保留别名**,以 44 回写为准。
- **锚点**:所有 cue 的 `Cell` = **医馆房间格**(与 F-18.1 的 `EnvMod` 同格,R-5-B 口径)——
  远端玩家按空间化听,取 ADR-018 §五 的复用第二 QoS 位置通道,**不新增通道**。
- **总线**:属 **SFX**;⚠️ **炉火声床不得被 `StethoscopeFocus` 压到消失**(NP/AD I4:听不见炉火 =
  等待期唯一的全程听觉证据被 UI 状态切换没收)。压音曲线数值归 44。
- **三护栏**(AD-1,镜像 44 自家纪律):
  1. **收尾自评 = `start + duration` 的纯函数**(承 AC-44-D7):起货音的播放时点由
     `CompleteTick`(F-18.3)推导,**禁**以「炉子对象还在响」为停播条件(冻结 / 换场景会破);
  2. **淡出窗口非帧对齐**(镜像 ADR-018 G1):火声随 `duration_ticks` 尾段的淡出是**时间窗参数**,
     实现者禁做逐帧包络积分;
  3. **等待期声床是「炉子还活着」的可听证据**,其形态 = **器具物理状态的连续投影**
     (火在烧就有声)⇒ **禁边界音形**(禁「点火成功!」 sting、禁「还剩 N 秒」节奏加密 ——
     后者同时违反 5 侧 B-8 禁时间积分的镜像:玩家不得用耳朵数 tick)。
- **禁**「制作完成 jingle / 成功提示音 / 失败提示音」—— **状态播报**,由 **AC-44-09** 断言。
  起货音的合法身份 = **行为反馈**(炉盖揭开的物理事件声),**不是**「恭喜出货」播报;
  去标注盲测判据见 **AC-18-22**(镜像 AC-5-10 形式)。
- **VR 模式的炮制音频推 P1b**(承 ADR-018 §七 与 44 的 VR 批次同批,不在 P0 关键路径)。

### UI-18.2 硬约束

- **零数字** —— 无转化率 / 无成功率 / 无进度百分比 / 无「品质 +15%」;
- **零按键提示浮层**(承 `AC-3-F1a`;炮制由 48 教);
- **不可发起 ≠ 灰置** —— 不满足准入的配方**不出现**(灰置 = 隐形提示,反幻想);
  ⚠️ **BL-8 口径**:「不出现」是**面板侧**禁令,**不等于配方不存在于世界**(规则十:
  出诊所见 / 医馆旧档 / 病家口述是世界侧可及通道);
- **不靠颜色** —— 成品成色以**质地 / 药签措辞**承载(承 V-8.2);
- **无声拒绝的物理事件面**(ux I4):准入拒绝不给文字/音效提示,但**料被搬回、火折子划不着**
  ∈ 白名单内物理事件(行为反馈)—— 拒绝须「看得见发生了拒绝」,不须「被告知拒绝了为什么」。

### UI-18.3 两栈归属声明(BL 补 · 承 ADR-013)

- **P0 无独立「炮制面板」screen** —— 选料复用 **20 出诊箱容器**;「配方列表 + 点火」的
  呈现落点 = **42 的屏闭集须补入炮制交互**(O-18-R6 接缝,与 **11 方笺并批**提给 42);
