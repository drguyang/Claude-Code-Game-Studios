## Context

### Problem Statement

51 的处境是一处**职责与规格的严重失衡**:

- `systems-index.md:255` —— **「51 遥测与分析 — 回答「**判断层到底好不好玩**」的仪器」**,
  绑定**支柱一「判断为骨」** —— 这是**全案最核心的设计问题**;
- `systems-index.md:85` —— 却是 `| 51 | 遥测与分析 | Foundation | P0 | **未开始** | — | — |`
  (**零依赖、零 GDD**);
- `systems-index.md:480` —— 估 **S**(1 次会话);
- `architecture-review-2026-09-15.md:88` —— **GDD ❌ / ADR 覆盖 ❌ 零**;
- **全案零 TR**:`tr-registry.yaml` 的 `system:` 值仅 7 个,不含遥测;
  唯一相关是 `TR-randomevents-024`(「事件与 51 遥测的边界」,`status: gap`,`adr: null`)——
  而该 requirement 的文本**在 `random-events.md` 内找不到落点**(疑仅在索引层生成)。

**不裁决的代价** —— 三条:

1. **默认滑向「AAA 式 live-ops 遥测」**:一个「遥测与分析」系统,若无权威件,最自然的默认
   是接入第三方分析 SDK、埋点上报。而这与本项目**四连的「运行期零第三方」取向**
   (ADR-014 零 JSON 解析器 · ADR-015 零第三方几何工具 · ADR-016 零第三方行为树 / 寻路库 ·
   ADR-017 零 DOTS)直接冲突,且引入**隐私面**(PC/Steam 单机 + P2P,本无任何出厂数据)。
2. **「判断层好不好玩」无从测量**:支柱一的核心问题若无可测手段,整个设计的验证闭环是空的
   (`systems-index.md:409/414` 要求 P0 有「看得见的难度曲线」,但门控项是 5 / 17,**不含 51**)。
3. **51 可能与「用户手调数值」冲突**:若 51 被写成「自动调平衡」,就与
   `feedback-user-owns-balance-values`(**数值用户自己调**)直接矛盾。

## Decision

**裁决:51 本地优先。遥测 = 确定性模拟的事件流回放产物;零第三方 SDK;零出厂数据;
51 住边界层并以只读消费者订阅三流;隐私面因「无出厂」而结构性满足;
P0 交付最小切面;线上化若日后需要另开 ADR。**

### 一、回放即完整数据记录(核心)

**ADR-005 的确定性模拟本身就是一台完整的记录仪。** 事件流是唯一真源、逐位可复现、
含全部状态变更;`case-system.md:162` 已保证病例「记录完整、可回放」;
`adr-005:316` 已写明回放使「联机核对、调试」受益。

⇒ **51 不需要埋点。「埋点」在本项目是一种**冗余** ——** 想知道的每一个量,
其真源**已经**在事件流里。51 的形态因此是**读数器**,不是**采集器**:

| 「判断层好不好玩」需要的量 | 真源(已存在) | 51 的动作 |
|--------------------------|-------------|----------|
| 判断准确率 | 病例流 `JudgmentRecorded` / `JudgmentRevised`(ADR-008) | 聚合 |
| 误诊分布 | 病例流 + 病史流 | 聚合 |
| 「跳过」率 | 事件流中的跳过事件(ADR-001 降级路径) | 聚合 |
| 熟练度成长 | 病史流 | 聚合 |
| 难度曲线 | 三流的时间分布(事件 Tick) | 聚合 |
| 局内时长 / 节律 | `Tick` 序列 | 派生 |

**AC-19-01**:上述每一项指标**可从既有事件流重算**,**无需任何新埋点**(BLOCKING)。
若某指标**无法**从事件流得出,处置是**先问「该状态是否本就该进流」**(ADR-009 的三问判据),
而**不是**给 51 加一条旁路采集 —— 旁路采集会造出「事件流之外的第二个真源」。

### 二、零第三方 SDK · 零出厂数据

**51 不引入任何第三方分析 / 崩溃上报 / 遥测 SDK;运行期不发生任何向设备外的数据传输。**

| 项 | 裁决 |
|----|------|
| 第三方分析 SDK(Unity Analytics / UGS / Firebase / …) | **不引入**。`docs/engine-reference/unity/` 对其**零覆盖** ⇒ 无权威件可依,不作承诺;且违背四连的零第三方取向 |
| 崩溃上报 SDK(Sentry / Backtrace / …) | **不引入**。崩溃数据是 51 的**相邻但不同**的关注点;若日后需要,按同一纪律评估(本地日志优先),另开 ADR |
| 玩家反馈渠道 | **不在 51 范围**。Steam 的评论 / 社区本就承担此职;51 不做内建反馈收集 |
| Steamworks 统计 / 成就 | **不在 51 范围,且当前不启用**。它们是**平台面**(玩家可见的成就),与「内部设计验证」用途不同 |

**AC-19-02(BLOCKING)**:构建产物与运行期**无任何网络上报调用** ——
静态扫描(无 telemetry HTTP 客户端)+ 运行期监控(无出站连接)双重断言。

**AC-19-03**:51 的输出**只落本地**(本地文件 / 调试视图);**不存在**「开启 / 关闭上报」的开关 ——
因为没有可开关的东西(这同时消解了「退出开关」需求)。

### 三、51 住边界层 —— 不进 sim,不写三流

```
┌────────────────────────────────────────────────────────────┐
│  sim 程序集(门 A:"noEngineReferences": true)             │
│  事件流(病史 / 病例 / 世界)—— 唯一真源                   │
│   ✗ 51 不进此程序集(它也零 UnityEngine,但职责不同:      │
│     51 是工具,不是模拟的一部分)                            │
└──────────────────────┬─────────────────────────────────────┘
                       │ 只读订阅(不写)
                       ▼
┌────────────────────────────────────────────────────────────┐
│  边界层 / 工具层                                            │
│  51 遥测与分析:读事件流 → 聚合成指标 → 本地文件 / 调试视图 │
│   ✗ 不写三流   ✗ 不是第四个 IEventSink 写入者               │
│   ✗ 不出厂     ✗ 无第三方 SDK                              │
└────────────────────────────────────────────────────────────┘
```

- **不进 sim**:51 是**工具 / 分析**关注点,不是模拟事实。放进 sim 会给门 A 增加一个
  与模拟正确性无关的引用面(且 51 的输出是「给人看的」,不是「给 Step 用的」)。
- **不写三流**:51 是**只读消费者**。若 51 能写流,它就成了真源的一部分 ——
  这会让「遥测」污染「模拟」,是最危险的一类越界(与 ADR-008 的 `salt_as_secrecy` 同类:
  **把一个非真源的东西放进真源**)。
- **不改 ADR-005 / 009 的任何裁决**。

**AC-19-04**:51 的程序集**不引用 sim 程序集以外的任何引擎程序集**,
且**不出现于任何 `IEventSink.Append` 的调用点**(grep 断言)。

### 四、隐私面 —— 因「无出厂」而结构性满足

**本项目的隐私答案之所以是「可结论的」,是因为它现在是空的:**

| 隐私问题 | 本裁决下的答案 |
|---------|--------------|
| 是否采集个人信息? | **否**。无账号、无邮箱、无设备指纹;存档内的玩家名是**本地**的,不出厂 |
| 是否需要隐私政策(游戏内拦截)? | **否** —— 因为没有任何数据离开设备。Steam 页面仍可写明「本游戏不收集数据」(那是对玩家的**告知**,不是**同意机制**) |
| 是否需要 GDPR / CCPA 合规机制(同意 / 导出 / 删除)? | **否** —— 无数据控制者角色;本地存档删除即玩家自己的操作 |
| 是否需要「遥测退出开关」? | **否** —— 无可退出的项(AC-19-03) |
| 联机时主机是否收集客户端数据? | **否**。合作模式下主机**不采集**客户端遥测(51 读的是**本地**事件流副本,ADR-005 的客户端流副本;且写入面为零) |

**AC-19-05**:发布清单的 Privacy / Analytics 项(`release-checklist-template.md:90,97-98`)
的答案固定为「无出厂数据 / 无第三方分析 / 无内建崩溃上报」。

> **⚠️ 本节的结论是「当前状态」的结论,不是「永远」的结论。**
> 一旦任何**出厂数据**被引入(哪怕只是 opt-in 的崩溃上报),
> **本 ADR 的 §四 即失效**,必须**另开 ADR** 重新处理同意 / 隐私政策 / 数据删除。
> 这一条是硬边界:**不得以「小改动」为名在既有 ADR 上打补丁。**

### 六、51 不得成为「替用户调数值」的替身

**数值用户自己调**(本项目一贯纪律)。51 的定位因此被**明确收窄**:

- 51 **交付**:**数据**(指标) + **可操作的观察结论**(如「该难度段跳过率异常高」);
- 51 **不交付**:**调好的数值**;**不自动改** `assets/data/*.json`;**不输出**「建议把 X 改成 Y」。

**理由**:若 51 自动调参,则(a)与用户的调参主权冲突;(b)调参是**设计判断**,
需要人对照医学语义与实际手感,不是统计量的函数;(c)**数值是用户手调的旋钮**,
51 最多让旋钮的**方向**更可见,不能替它转。

**AC-19-07**:51 的输出为**只读数据 / 报告**;不存在任何写回 `assets/data/` 的代码路径。

**结清方式:52 与 51 之间**不需要**新契约。**

- 52 的产出**已经**落三流(`EventRolled` / `EventArrived` / `ThreatDeferred` /
  `ThreatDeferralCleared` / `HistoryFlagChanged`,ADR-007);
- 51 **只读**这些流(§三),**不向 52 索要专门字段**,**不向 52 写回**;
- 因此 `TR-randomevents-024`(「事件与 51 遥测的边界」)的答案是:
  **边界 = 三流本身** —— 52 只管写流,51 只管读流,二者**零直接接口**。

**AC-19-08**:`TR-randomevents-024` 由 `gap` → `covered`,adr = 本 ADR;
**注**:该 requirement 在 `random-events.md` 内无落点(疑仅索引层生成),
其语义由本 ADR §一 / §三 承接。

### Architecture

### Implementation Guidelines

1. **先问真源,再加代码。** 想测一个量之前,先问「它是否已在事件流里」。
   若不在 —— 用 ADR-009 的三问判据判断**它是否本就该进流**,而不是给 51 加旁路采集。
2. **不要加网络。** 任何 `HttpClient` / `UnityWebRequest` / 第三方 SDK 的出现都是 AC-19-02 的失败。
3. **不要加玩家可见的统计 UI**(§五 / AC-19-06)。
4. **不要把 51 放进 sim 程序集。** 它是工具,不是模拟的一部分。
5. **不要写回 `assets/data/`。** 51 只读数据、只出报告(§六 / AC-19-07)。
6. **崩溃上报不在本 ADR 范围。** 若需要,按其纪律(本地日志优先)**另开 ADR** —— 
   且一旦出厂,§四 即失效。

## Alternatives Considered

### Alternative 1: 本地优先 —— 回放即数据记录,零第三方(本裁决)

- **Description**:51 = 事件流的只读读数器;零 SDK、零出厂;本地文件 + 调试视图。
- **Pros**:复用已有真源(零埋点);与四连的零第三方取向一致;隐私面结构性干净;
  P0 窗口零范围债;`TR-randomevents-024` 自然结清(边界 = 三流本身)。
- **Cons**:无法获得**玩家群体**数据(只有开发者的本地会话)—— 但对单机 indie
  且「验证设计是否好玩」的目标而言,**开发者自己的会话 + playtest** 本就是主渠道。
- **Estimated Effort**:小(S 档成立)。
- **Rejection Reason**:**采纳**。

### Alternative 2: 接入第三方分析 SDK(Unity Analytics / UGS)

- **Description**:接入 UGS 或同类,上报匿名事件。
- **Pros**:可获群体数据;有现成仪表盘。
- **Cons**:违背零第三方取向;引入隐私面(需同意 / 政策 / 删除);
  `docs/engine-reference/unity/` 对其**零覆盖** ⇒ 无权威件;**本机无法联网核查条款** ⇒
  无法做尽职调查;且**规模上无收益**(单机 indie 的玩家基数不足以支撑统计推断)。
- **Estimated Effort**:中(集成 + 隐私机制 + 合规)。
- **Rejection Reason**:**收益与判据均不成立,成本与风险成立**。

### Alternative 3: 自建轻量上报端点

- **Description**:自建一个接收端点,POST 汇总指标。
- **Pros**:避开第三方;数据自持。
- **Cons**:**仍需运维基础设施**(P0 无服务器);仍出厂数据(隐私面回归);
  仍是范围债;且**没有任何 P0 需求**要求出厂。
- **Estimated Effort**:中–大(端点 + 运维 + 合规)。
- **Rejection Reason**:**为不存在的需求建基础设施**。

### Alternative 4: 在 sim 内埋点(51 进 sim 程序集)

- **Description**:让 51 在 sim 的 Step 里直接采集。
- **Pros**:采集最「实时」。
- **Cons**:给门 A 增加与模拟正确性无关的引用面;且易滑向「51 写流」⇒ 遥测污染真源;
  且 51 的输出是「给人看的」,不该住「给 Step 用」的程序集。
- **Estimated Effort**:小(看似)。
- **Rejection Reason**:**越界风险 + 门 A 污染**。

### Alternative 5: 51 不做,P0 裁撤

- **Description**:把 51 移出 P0,留待 P1。
- **Pros**:省一个 S 档。
- **Cons**:支柱一的验证闭环**空掉** —— 「判断层好不好玩」无从测量;
  而 `systems-index.md:414` 要求 P0 有「看得见的难度曲线」,却**没有**一个系统承担验证它;
  且本裁决下 51 的成本**已经很小**(复用事件流,零新管道)。
- **Estimated Effort**:0(但留下验证缺口)。
- **Rejection Reason**:**成本已很小,而它承担的问题极核心**;裁撤的收益不抵验证漏洞。
  (若用户日后想裁,本 ADR §五 的最小切面已把成本压到最低。)

## Consequences

### Positive

- **支柱一「判断为骨」获得可测手段** —— 「判断层好不好玩」从口号变为可重算的指标。
- **零埋点**:51 = 读数器,真源已存在(复用而非新建)。
- **隐私面结构性干净**:无出厂 ⇒ 无同意 / 无政策拦截 / 无删除机制 / 无退出开关。
- **`TR-randomevents-024` 结清**:52 ↔ 51 边界 = 三流本身,零直接接口。
- **P0 窗口零范围债**:S 档成立,且不引入任何新管道 / 依赖。
- **与用户调参主权一致**:51 交数据不交数值(§六)。

### Negative

- **无玩家群体数据** —— 只有本地会话 + playtest。缓解:对单机 indie 而言这**本就是主渠道**;
  若日后需要,走 §四 的「另开 ADR」路径(且须先解决隐私面)。
- **「判断层好不好玩」的结论依赖开发者自己的会话量** —— 缓解:playtest 证据本就适用于
  Visual/UI/Config 类(`coding-standards.md` Test Evidence 表),51 是它的**量化补充**。
- **§四 的隐私结论是「条件性」的**(一旦出厂即失效)—— 但这是**特性**而非缺陷:
  它把边界写得清楚,让「加一点上报」无法偷偷发生。

### Neutral

- **`analytics-engineer` 的定位**明确:在 P0 是**本地指标的重算与解读**,
  不是「搭数据管道」。其价值在**问对指标**,不在**采集**。
- **Steam Cloud Saves**(`architecture-review-2026-09-15.md:340` 记为「需另决」)
  仍是**开放项**,不在本 ADR 范围 —— 但本 ADR 的「零出厂」不排除它
  (云存档是**玩家自己的存档上云**,不是遥测;另决)。
