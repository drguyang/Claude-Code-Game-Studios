## Overview

**3 输入与设备是全案唯一「玩家的手」与「游戏世界」之间的那道转换层。**

从技术上说,3 是**架构复核 §2 记为零覆盖的系统**(GDD ❌ / 架构覆盖 ❌ 零)——
它的三条约束(`TR-concept-007` 急救 <50 ms · `TR-concept-008` 手柄焦点导航 · `design/ux/` 不存在)
全部是 gap,直到 ADR-011 落盘。3 的职责只有四条:
**① 把物理输入映射为动作**(一套动作资产,K&M + Gamepad + OpenXR 三套绑重);
**② 把动作持久化为绑重 overrides**(输入层**唯一**的落盘职责,ADR-010 之外);
**③ 把「手感量」与「判定量」分开** —— 急救动作走**独立直读通道**(<50 ms,**不穿过 42 UI 事件栈**),
直读浮点值是手感层(不进流),交出的读数是**全整数的 `EmergencyReading`**(tick 计持时 + 边沿);
**④ 把导航动作映射为 `FocusNavigationIntent` 单向只读视图**(接口归 3,**焦点移动的唯一真源 = 官方桥,归 42/R-6** ——
D-A 裁定:**意图不驱动移动**)。
3 **不产生任何 `SimEvent`、不写三流、不持有游戏状态** —— 它产出的是**意图**
(`InteractIntent` / `EmergencyIntent` / `FocusNavigationIntent`)与**全整数急救读数 `EmergencyReading`**;
**判定(`Judge` / `JudgeResult` / `SimEvent`)全归 10** —— `SimEvent` 由 10 构造并 `Append`(规则八 / 九 · `AC-3-A6`)。
> **⚠️ 三轮评审修正(生产者口径)** —— 初稿把判定记在 3 名下,先后写成「3 直接构造 `SimEvent`」
> 与「3 产出全整数判定结果 `JudgeResult`」(两处均在本 Overview ③ 附近)。**两处同病**:3 只出**读数**,不出**判定**。
> 全文已统一;`EmergencyReading` 是 3 与 10 的边界类型(`IEmergencyInput` 的产物)。

从玩家侧说,3 是「**你感觉不到它**」的那一层。它做得好,玩家会以为是自己的手很稳;
它做得不好(延迟、卡键、焦点跳错行、改了键下次开机又变回来),玩家会以为是游戏坏了。
**3 的全部设计目标是「零存在感」**:无按键提示浮层(依据 = `technical-preferences.md:33`
拟物 UI 双导航硬约束 + `AC-8-43/44`;**不是支柱五**)、无输入延迟可被察觉、无手柄焦点路径断头。

> **评审后口径修正(2026-09-15)**:本 GDD 初稿宣称「3 保护了这个幻想」。评审裁定**只对一半** ——
> 3 保护的是**前提**(意图不泄漏进 sim),而幻想本身(**「手稳」小游戏**)全案**无主**:容差窗口 /
> 抖动模型 / 失败反馈 / 技能→窗口缩放四处皆空,而 `game-concept.md:695` 已点名两个动作
> (心肺复苏 = **节奏** / 止血包扎 = **顺序与力道**)。**归属已登记为 10 的债务**(见 §Dependencies 五)。
> 另:`< 50 ms` 是**前提**不是开关 —— 杀死「手稳」的是**抖动(方差)**,不是均值(F-3.3 已据此重写)。

> **本 GDD 已锁定的口径**(2026-09-15 用户裁定,均照准;评审后补 ③④):
> ① **P0 不交付改键 UI** —— 3 在 P0 只交付「动作映射契约 + overrides 读写能力 + 默认三套绑重」,
> **改键界面推 P1a**(P0 范围阶梯 = 一间医馆 + 一个小场景 + 2 个急救动作 + 两条武器线,
> 改键页不在其中)。**能力已备、界面未交付** —— 这是**有意**的欠账,不是遗漏。
> ③ **①的前提(评审补:**由 creative-director 指出,用户照准)**:支柱一替裁定①兜了底 ——
> **每个动作都有跳过路径**,故运动障碍玩家不必完成小游戏。**但跳过路径本身必须是
> 焦点可导航、无时序要求、无模拟量的普通选择**;否则 P0 核心循环对这类玩家**完全没有出口**。
> **该路径归 10 急救动作**(已登记,见 §Dependencies 五)。
> ② **3 产出「绑定 → 图标键」映射,呈现归 42 / 48** —— 3 只回答「这个动作当前绑到哪个输入」,
> 返回 `iconKey`,**是键名不是素材**;且是**抽象按钮 id**(如 `"Kbd.E"` / `"Pad.South"`),
> **不含厂商字形与颜色**(颜色编码的按钮 = 经典的色盲陷阱;字形随平台映射归 42)。
> **素材、出现时机、是否显示** 全部归 42(渲染)/ 48(教学)。
> ④ **反幻想条款的执行强度 = 强制执行(评审补,用户照准)**:初稿写「守门责任落在 42 / 48」

> **42 + 48 联合 BLOCKING AC(AC-3-F1a / F1b)** —— 仅写设计意图不开 AC 已于 2026-09-15 被否。

3 **不拥有**:急救判定与熟练度结算(10 / 30)· 焦点移动与焦点算法(42 / R-6)·
移动与视角手感数值(1 / 2)· 存档(7a / ADR-010)· UI 内容与素材(42 / 43 / 39 / 7b / 48)·
震动触觉的**语义**(8 / 10 —— 3 只拥有**通道**)。

> **实现 → ADR**:动作资产组织、直读通道、绑重持久化、焦点导航接口的形状**全部承 ADR-011**;
> 本 GDD 只描述**动作清单 · 设备态 · 边界与验收**,不重定架构。
> **⚠️ 但初稿的多数严重缺陷是「忠实继承」ADR-011 的未推导断言,而非自创**(评审裁定)。

## Player Fantasy

**「你的手就是你的手。」** —— 3 的幻想是**没有幻想**。玩家永远不该想到输入系统。

- **手稳 = 判定准。** 急救动作是「手稳」的小游戏(ADR-011 §二)。**任何可察觉的延迟
  都会把「我的手法不行」翻译成「这游戏卡」** —— 幻想当场破产,而且玩家**不会知道该怪谁**。
  <50 ms 不是一个性能指标,是**这一个幻想是否存在的开关**。
- **没有按键提示。** 依据 = `technical-preferences.md:33` 的拟物 UI 双导航硬约束 +
  `AC-8-43/44`(`AC-8-44` 原文明写「**且无任何提示文案**」):**玩家永远不该在屏幕角上看到
  「按 E 交互」**。要教操作,用**环境**(48 的示范、口述、纸上的图),不用浮层 ——
  3 因此**只给键名,不给素材、不决定时机**(用户裁定②)。
  > **评审后修正(2026-09-15)**:初稿此处写「支柱五」是**误引**(支柱五 = 史实为骨,架空为肉)。
  > 更要紧的是,3 只给键名的代价是**反幻想无人接棒** —— 初稿还在 §Visual/Audio 二
  > 预先写好了免责(「教学期的按键提示若出现,那是 48 的设计决定」)。已按 2026-09-15
  > 用户裁定改为**强制执行**:42 + 48 联合 BLOCKING AC(AC-3-F1a / F1b)。
- **手柄不是二等公民。** 手柄没有指针,而本作的脉案 / 出诊箱 / 纸质地图**全是纸**。
  焦点导航断了,手柄玩家**连门都进不去** —— 这不是「体验差一点」,是**不可玩**。
  3 的职责边界停在这里:**把导航动作变成意图**,剩下的交给 42。
- **反幻想**:玩家**永远不会**看到「输入中……」「重新绑定成功」这类对话框(P0 无改键 UI);
  **永远不会**看到灰掉的按钮(承 `diagnosis-system.md:1864` `AC-8-44` —— P0 没有不可用动作);
  **永远不会**在改键后下次开机发现键变了(P0 根本没有改键入口)。

> **锚点**:`game-concept.md:194`(支柱一「判断为骨,手感为肉」)·
> `technical-preferences.md:33`(「拟物 UI **必须同时支持键鼠与手柄导航**」)·
> `technical-preferences.md` 性能预算(「急救动作输入延迟 < 50 ms —— 手感小游戏的核心是『手稳』,
> 延迟直接杀死它」)。

## Detailed Design

### Core Rules

> 3 的规则分四组:**映射**(物理输入 → 动作)· **持久化**(绑重 overrides)·
> **分流**(手感层 vs 判定层)· **导航**(动作 → 焦点意图)。每条后面标出处 ——
> 3 的绝大多数边界**不是本 GDD 新立的,是 ADR-011 强加的**,本节的职责是把它们落到可实现的口径。

#### 一、映射:一套动作资产,一份动作清单

**规则一 · 全案只有一个动作资产。** 一个 `.inputactions`,内含全部 action map。
**UI 模块必须引用同一资产**(`InputSystemUIInputModule` 的 UI 动作映射指向同一文件的 UI map)。

> **⚠️ 评审后修正(2026-09-15)**:初稿的理由写的是「两套资产 = 分叉 = **同键双触发**」——
> **这是非因果的**。两套资产的真实后果是 **GUID 分叉 + override 命名空间分裂**
> (「这个改键是改给谁的」无解),不是双触发;**双触发的真纪律在规则十二**。
> 本规则保留**单一资产**,理由已改正为「**单一 override / 改键命名空间**」。
> **新增硬约束**:每玩家资产副本(规则六)**不得启用 UI map** —— 否则 N 份副本 =
> N 个 `NavigationMoveEvent` 源,**那才是真的同键双触发**(初稿把这条错误地归因给了「两套资产」)。
> **AC-3-A1(BLOCKING)** 守门(判据已由「文件计数 = 1」改为**单引用同一性**,见 AC 组:
> 引擎自带示例 `.inputactions` 会让计数判据当日即红)。

**规则三 · 三套绑重 + 通用布局。** K&M / Gamepad / OpenXR 三套绑重**同表共存**;

共享 = 移动镜头的同时焦点乱跳)。**`AC-2-22`⑥(`O-16`)的对侧落点 = 本条**:

`Navigate` 与 `Look` 的控件分离是其中一对**具体实例**(2026-09-20 回刷:2 的 `AC-2-22` 实测
6 项中此项「尚未登记」—— 本规则即该登记,`AC-2-22`⑥ 由此可从红转验)。

#### 二、持久化:绑重 overrides 是输入层唯一的落盘职责

**规则四 · 3 的落盘面 = 一组 sidecar(头部 + 载荷,**两文件**),且**载荷用出厂 API**。** `bindings overrides` 序列化到**输入层自己的文件组**,
**不进 ADR-010 的存档、不进三流**(承 ADR-011 §一 + ADR-010 §三)。
> **四轮评审修正(命题级 sweep · 就地覆写)** —— 本规则标题原文为「**3 只落一个文件**」,
> 与本节下方的 **sidecar 两文件布局**(`:174-177`)**直接矛盾**,且该旧命题曾在 `AC-3-A5` 与
> §五 边界清单两处被当作判据引用。**旧命题「一个文件」已全量废除**,以「**一组 sidecar(两文件)**」取代;
> 残留的三处引用同批就地覆写(规则四标题 · §五 边界清单 · `AC-3-A5`)。
> **失效机理**:实现者若按旧命题做单文件写盘,则 `AC-3-A3` / `AC-3-A8` 的**字节往返前提不成立**。
> **评审后修正(2026-09-15)**:**override 载荷用出厂 `SaveBindingOverridesAsJson()` /
> `LoadBindingOverridesFromJson()`**(`docs/engine-reference/unity/modules/input.md:269-274`),不自己写序列化器。
> 初稿**只字未提**这两个 API —— 手写 = 重新实现一遍 GUID→override 的键方案,并在接缝处写错。
> **本 GDD 的文件 = 自带头部(hash + 版本)+ 出厂 JSON 载荷**;头部归 3,载荷归引擎。
> **禁写集新增 `PlayerPrefs` / `EditorPrefs`**(否则照抄引擎文档示例的实现会当场违反 AC-3-A5)。
>
> **⛔ 头部与载荷的物理布局(三轮评审补 —— 初稿从未定死,是静默失效的入口)**:
> **头部必须放在 `LoadBindingOverridesFromJson()` 读的 JSON 之外** —— 因为该 API 只接受
> **它自己写出的那份载荷**;把自定义头部字段**塞进同一份 JSON** 会:
> ① 使引擎解析器读到不认识的键(行为随版本未承诺);② 逼 3 在读出时**重新序列化 / 剥离头部**
> ⇒ 喂给 `Load…` 的字节**不再逐字节等于** `Save…` 写出的字节 ⇒ 解析路径分叉。
> **定死布局 = sidecar**:同一目录下两文件 ——
> `bindings.overrides.json`(**原样** `Save…` 的输出,**逐字节**喂 `Load…`,3 **不解析、不重写**)
> + `bindings.schema.txt`(3 自己的头部:**schema hash · 格式版本 · 写入用的动作资产 id/版本**)。
> **读序**:先读 sidecar 头部 → 比对 schema hash → (匹配)把 overrides 文件**原样**喂 `Load…`;
> (失配)走规则五第 4 步。**AC-3-A3 / `AC-3-A5` 守门**,须含「喂入字节 == 保存字节」的往返断言。

**规则五 · 资产重建必须优雅失效,不能静默。** overrides 按 action 资产内 binding 的
**GUID(id)** 匹配 —— **资产重建(整文件重新生成)⇒ GUID 全变 ⇒ overrides 静默全部失效**
(无报错、无提示,玩家只觉得「我的键又变回去了」)。四步防线(承 F3,评审后补第 2 步):

1. `asset.Disable()`;
2. **`asset.RemoveAllBindingOverrides()`** —— **评审补**:`Disable()` **不移除**已载入的 override,
   override 是**叠加**的,不清理会在新载荷上**留下陈旧条目**(初稿把失败模式描述为「存在两份绑定」,不准确);
3. **overrides 文件头存槽位签名 hash**(§F-3.5,**已含 binding `id`**);
4. **hash 失配 → 优雅清空**:保留旧文件(改名备份)+ 载入默认绑定 + **记一条日志**。
   然后 `Load…` → `Enable()`。**不静默采用错位的 override**(那才是灾难),
   **也不弹窗**(P0 无改键 UI,弹窗无处可去)。
> **明确取舍**:失配时玩家**失去全部改键**而不是**得到错位的改键** ——
> 前者是可恢复的不便,后者是**贴错标签的操作**(按 A 触发 B)且玩家无法诊断。
> **AC-3-A3(BLOCKING)** 守门。
> **⚠️ 初稿的 hash 对它自己的这个失效完全盲**(评审裁定,见 F-3.5):只哈希结构路径 ⇒
> 结构保持的重建**不改 hash** ⇒ 判为匹配 ⇒ overrides 照样静默全丢。**hash 必须含 binding `id`。**

**规则六 · 同机多玩家 = 每玩家一份资产副本(不得启用 UI map)。** 1-4 人**同机共进程**时,
每玩家实例化一份 `InputActionAsset`;纯联机(每人一机)时**不实例化**(低危)。承 F3。
> **评审后修正(2026-09-15)**:① 运行时实例化 API 是 **`InputActionAsset.Instantiate()`**
> (初稿写 `Clone()`,**待对 Input System 实际版本 spike 核对** —— `Compatibility`/旧名残留;
> ⚠️ **四轮**:`Instantiate()` 与 `Clone()` 在引擎参考库中**同样零覆盖** ⇒ 规则层保留符号名,
> 汇总册页 = `adr-011` §Risks-A S2,**判据层只断实例同一性** —— 见 `AC-3-A1`);
> ② **副本不继承 binding overrides**(`Save/LoadBindingOverridesAsJson` 是**逐实例**的)——
> 须显式播散;③ 初稿未考虑 **`PlayerInput` / `PlayerInputManager`** —— 引擎**自带**的同机多人机制,
> 它会替本规则做掉克隆 / 设备配对 / scheme 切换**三件手写活**;**P1b 时应优先评估它**;
> ④ **副本不得启用 UI map**(否则 N 个 `NavigationMoveEvent` 源,见规则一)。
> **P0 不涉及**(P0 = 单人,`game-concept.md:27` 联机是 P1b),但**形状现在定** ——
> 事后改 = 动作资产的持有方式重写。**P1b 实现**,见 `OQ-3-3`;内存与每帧 action-state 求值
> 随人数线性增长,**P1b 须带实测义务**(评审登记)。

#### 三、分流:手感层与判定层是两条路

**规则七 · 急救直读通道独立于 42 UI 栈,且走回调不走轮询。** 急救动作的输入值
**在 `InputSystem.onAfterUpdate` 期的 action 回调中取**(**评审后修正**:回调在输入更新期内触发,
**早于** `MonoBehaviour.Update`,延迟**严格更低**;初稿把「`Update` 或专用回调」当作等价选项,
**不等价**)。
> ⚠️ **须 spike(四轮)** —— `InputSystem.onAfterUpdate` 的**相位**在引擎参考库中**零覆盖**
> (`docs/engine-reference/unity/modules/input.md` 356 行只含 overrides 两个 API);
> **规则层保留符号名,汇总册页 = `adr-011` §Risks-A S3**(判据层**只断性质**:采样点每帧恰一次
> 且相位确定 —— 见 `AC-3-B1b` 的归属段)。
> **为什么必须绕过 UI 栈 —— 理由已改正(评审)**:初稿写「UI 栈有排队与焦点路由延迟,会吃掉
> <50 ms 预算」并称其为「**算术原因**」。但 UI 事件路由是**帧内调度**成本,与 `L_render`
> (呈现延迟)**无关** ⇒ **绕过 UI 栈在算术上改变不了 `L_input→pixel`**,初稿的算术不成立。
> **正确的理由是「抖动与调度确定性」**:事件排队 / 焦点路由会引入**不定帧数**的延迟,
> 而杀死「手稳」的是**方差**不是均值(40–45 行 F-3.3 已据此重写)。**结论对,理由错 —— 结论保留。**
> **连带硬约束**:`InputSystem.settings.updateMode` 必须**钉死并实测**(Dynamic / Fixed / Manual
> 直接改变 `L_poll`;初稿称 `L_poll`「不可调」是错的 —— `Manual` 模式允许自行调 `InputSystem.Update()`)。
> **AC-3-B2(BLOCKING)** 守门,判据 = **asmdef 断言 + Roslyn 分析器**(非「调用图断言」)。

**规则八 · 直读浮点值是手感层,永不进流;3 交出的是整数读数,不是判定。**
`ReadValue<>()` 返回的 `float` 只用于**当下这一帧的手感与表现**,**不构成任何 `SimEvent` 载荷**。
**3 交给 10 的是 `EmergencyReading`** —— 持按时长**以 tick 计**(整数)、按压 / 松开**边沿**(整数)、
`EmergencyAction` 枚举索引;**它的每一个字段都必须是整数语义**。
熟练度修正系数一类**分数**用 **`FixParse.FromRatio(long, long)`**(取**整数**入参,**无浮点路径**)表达。
**`Judge(...)` 与 `JudgeResult` 归 10** —— 3 **不做判定、不产出判定结果**。

> **⚠️ 评审修正一(`FixParse` 范畴错误)**:初稿写 `JudgeResult → FixParse → IEventSink`。
> 按 `adr-006:105-122`,`FixParse` 类有**两个成员**,口径**不同**:
> - **`FixParse.Parse(string)`** —— **唯一的字符串 → `Fix` 入口**、**导入期**运行、**拒浮点字面量**;
> - **`FixParse.FromRatio(long, long)`** —— 取**整数**入参,**无浮点路径**,运行期可用(ADR-006 的整数构造)。
> 同处明写「**运行期不存在从 `float` 到 `Fix` 的路径 —— 编译期就不可表达**」。
> ⇒ 一个**运行期**的判定结果不可能喂给 `Parse(string)`,除非把浮点**字符串化再解析** ——
> 那正是 ADR-006 要堵的**第二条浮点路径**。
> **正确口径**:运行期用 **`FromRatio(long, long)` / 整数构造**;
> **`Parse(string)` 只服务作者态数据文件**(ADR-014 管线)。
>
> **⚠️ 三轮评审修正(禁止②的指代歧义)**:初稿的「**运行期调用 `FixParse`**」**指代不清** ——
> F-3.4 的禁止② 据此被读成「整个类禁用」,与「运行期用 `FromRatio`」**正面冲突**。
> **现明确**:禁止② 只禁 **`FixParse.Parse(string)`**(字符串入口);**`FromRatio` 不在禁列**。
>
> **⚠️ 评审修正二(浮点泄漏的具体路径,这是本清单唯一能污染确定性内核的项)**:
> 若判定结果由浮点算出,则 **持按时长(浮点)**会顺着
> `Judge(...) → 熟练度修正系数(C5 要求它是**分数**)→ JudgeResult → SimEvent` **流进流**
> (三者**全在 10 侧**;3 只交出整数 `EmergencyReading`)。
> 而 **「载荷路径上以结构体字段身份进来的 `float`」在设置 `AC-3-A7` 之前没有任何机械门覆盖**
> —— `AC-3-A6` 现在是 **asmdef 引用集断言**(管「不引用声明 `SimEvent` 的程序集」),**与字段类型无关**;
> `AC-3-B3` 只管 `JudgeResult` 的**顶层**字段。
> **新 AC-3-A7(BLOCKING)**:`SimEvent` 载荷路径上**不存在可达的 `float` / `double` 字段**。
>
> **一句话口径**(三轮修订):「**3 只出整数读数与意图;判定(`JudgeResult` / `SimEvent`)全归 10**」。

**规则九 · 判定归属分单机与联机(承 F1 · ⚠️ 2026-09-20 回刷:联机段改判为 ADR-011 Amendment B 口径)。**
- **单机**:判定走 9 / 10 的逻辑域(判断 + 熟练度),直读通道**只做手感**;
- **联机(ADR-011 Amendment B,C 路 · 2026-09-18 改判,取代原 F1「本地即时」)**:客户端把急救动作**聚合为一条全整数意图事件** `EmergencyAttempt` 上行;主机执行 `Judge` + `Append` + 发号 `Seq`。**本地即时判定降级为预表现**(不写流、不参与权威)。判定**不在本地出权威结果**。
  **「不逐帧同步输入」保留**(原 F1 正确的一半);`L_input < 50 ms` 是「输入 → 呈现」预算,不是「权威归属」预算(ADR-011 Amendment B)。
  **若判定走主机权威,反馈 = RTT,必然破 <50 ms 预算** 的旧推论**作废**——玩家对「事件何时进流」不可感知,对「体征何时变」本就延迟一个 tick。
> 这与 ADR-009 的拾取**完全同构**(意图进流、判定主机当下做、本地预表现)——2026-09-18 前急救侧自己的例外**已撤销**。
> 客户端上行 `EmergencyAttempt` 走**可靠通道**(ADR-001 **§一之三 裁决一**,2026-09-23 窄修订结清 `OQ-10-9` ≡ `QQ-14` —— 判定输入类**不走**第二 QoS;第二 QoS 仍只承载表现态位置)。

#### 四、导航:焦点移动的唯一真源 = 官方桥,3 只出只读意图视图

**规则十 · 导航动作只出一个类型化只读视图,不返回值、不驱动移动;焦点移动的唯一真源 = 官方桥。**
导航动作 → `FocusNavigationIntent`(承 F2:单向,不返回值 —— **焦点位置的真相在 42,不在 3**)。
> **⚠️ 三轮评审修正(D-A · 单一真源 · 用户裁定「官方桥为唯一真源」)**:初稿**留了两条路却没定真源**,

> **路 A**(3 的 `Navigate` 另进 UI map)⇒ 官方桥已产 `NavigationMoveEvent`,3 再发意图即 `AC-3-C2` 禁止的双触发;

> `PagePrev`/`PageNext` 无需映到 `FocusDirection`(42 / 39 直接消费的按钮)·
> **Tab / Shift+Tab** 由官方桥的默认绑定承载 · **`Navigate`(连续 `Vector2`)→ 离散步进**归官方桥 / 42
> (**F-3.2 已把连发改给 42**,与本节同向)。

**规则十一 · 3 不实现焦点移动。** 焦点算法、`FocusController`、唯一栈门**全归 42**
(承 ADR-013:用官方 `NavigationMoveEvent` 桥)。3 的职责**停在**「导航动作 → 意图(只读视图)」。

**规则十二 · 焦点单栈门由 42 守;3 不得制造双触发条件。**
见规则一(单资产 + 副本不启 UI map);另:在**单一真源**(规则十)之下,双触发的唯一残余面是
**喂 `Navigate` 的物理控件又喂了第二个焦点动作** —— 该条从「行为断言」变为**结构性构造断言**。

**规则十三 · ~~某一栈持有焦点时世界意图必须被抑制~~ —— 已整条删除(复审裁定 2026-09-15)。**
> **删除理由**:本规则要求 3 持有一个「是否有栈持焦点」的布尔,并据此**有条件地不发世界意图** ——

> 4 本就「决定这一帧的交互对象是谁」(见 §Interactions 表),由它按模态状态过滤。
> **3 不新增状态、不新增接口、不新增字段。**

> 且复审发现它是**无路由的接口**;现正式作废。

> **`AC-3-C5` 同进退**(已删,见 C 组注)。

> **⚠️ F-3.2(焦点重复速率)已整块删除(评审裁定)** —— 转归 **42**:
> ① 官方 `InputSystemUIInputModule` 桥只提供**固定** `moveRepeatDelay` / `moveRepeatRate`
> (该 API 细节**仓内无记载,须 spike**),而 ADR-013 强制 42 走官方桥且**不得自实现焦点移动**
> ⇒ **F-3.2 的加速曲线与 AC-3-C2/C4 结构性冲突**;
> ② 即便能自实现,加速连发**敌视本作点名的那个 UI** —— 病名册是**遇序、无检索、无索引、只增**
> (`diagnosis-system.md` UI-8.4),`REPEAT_STEP > 0` 会让玩家在长列表上冲过目标;
> ③ 该旋钮初稿自己已判给「42 的 UI 手感」,却又列在 3 的旋钮表里 —— **归属自相矛盾**。
> **结论**:删除 F-3.2 与 `REPEAT_*` 全部旋钮/AC,连同病名册的信息架构诊断一并转 42 / 39。

## Formulas

> **⚠️ 数值归属**(项目铁律):**下列全部常量由用户手调**,3 只交付**公式形状 + 变量表 + 安全范围**。

### F-3.1 死区与响应曲线(手感层)

> **用途**:摇杆 / 触控板的原始轴 → 可用轴。**纯手感层,永不进流**(规则八)。
> **消费者**:1(移动)· 2(视角)—— 二者的**曲线指数归各自 GDD**,本式只给**归一化形状**。

```
raw ∈ ℝ²                     摇杆为二维;单轴触发器的 raw_y ≡ 0
m   = ‖raw‖₂                                        ← 半径,非逐分量
t   = clamp((m − DZ_INNER) / (DZ_OUTER − DZ_INNER), 0, 1)
g   = (3t² − 2t³) ^ CURVE_POW                       ← smoothstep^P;**P > 1/2 才有两端 C1**
out = (raw / m) × g          if m > 0  ∧  raw 全为有限值
    = (0, 0)                 if m = 0  ∨  raw 含 NaN/∞
```

| 变量 | 含义 | 安全范围 | 破了会怎样 |
|------|------|---------|-----------|
| `DZ_INNER` | 摇杆漂移的忽略门槛 | `0 ≤ DZ_INNER < DZ_OUTER ≤ 1` | 太大 → **推到底也不满速**(移速可感知地变慢) |
| `DZ_OUTER` | 归一化终点 | 同上 | 太小 → **曲线陡到不可微调**(手指一动就到底) |
| `CURVE_POW` | 响应曲线指数 | **`> 1/2`**,上限由用户定(建议 `≤ 3`) | **`≤ 1/2` → C1 不成立**(见下方 Ⓐ);`< 1` → 前段过激(轻推就冲);`> 1` → 前段过钝(推一半才动);**无上限时大指数在定点下前段塌成 0** |

> **① 径向(radial),不逐分量** —— 初稿对 `x`/`y` 各自算死区与曲线,**这对圆形摇杆是错的**:
> 逐分量死区把可动区域切成了**方形**,顶点区域(斜向)与正向的行程不等 ——
> 归一化后**斜向速度 ≈ √2 × 正向速度**(+41%),表现为「斜着走更快」。
> 径向 = 用 `‖raw‖` 定大小、用 `raw/‖raw‖` 定方向,**逐向等速**。
>
> **② C1 软肩(评审修正)** —— 初稿在 `m ≥ DZ_OUTER` 处**硬截断到 1**:
> 左侧斜率 ≠ 0、右侧斜率 = 0 ⇒ **满速处有折角**。摇杆推到边缘时会产生
> 「推到底后再推一点没有反馈」的阶跃感。`smoothstep` 内嵌使 `g'(0) = g'(1) = 0`:
> **死区出口与满速端点都无折角**。代价:中段比纯 `t^P` 略平 —— 这正是**抗抖**想要的。
>
> **③ NaN / 零点防护(评审补)** —— 设备热插拔的一帧内可能出现 `raw = (0,0)`
> 或 NaN(驱动异常)。`raw / m` 在 `m = 0` 时**除零 ⇒ NaN ⇒ 污染整个表现层**。
> 上式先判 `m > 0` 且**全有限**,否则直接归零。**这一条是 `NoDevice` 态的算术落点。**
>
> **④ 常量写法归 ADR-014(用户裁定③)** —— `DZ_INNER` / `DZ_OUTER` / `CURVE_POW`
> **不是 `float` 字面量**,是**比值化 `Fix`**:创作态写 `"DZ_INNER": "1/8"`、
> `"DZ_OUTER": "7/8"`、`"CURVE_POW": "3/2"`,经 `FixParse.FromRatio(long, long)` 解析
> (承 `adr-006:105-122` 的唯一入口;**运行期不存在 `float → Fix` 路径**)。
> **本 GDD 不新立非确定性域资产** —— 复用既有 ADR-014 管线。
>
> **硬约束**:`DZ_INNER < DZ_OUTER`(相等 = `t` 分母为 0 → 除零)。
> **须在装载期断言**(承 ADR-014 区间校验纪律)。
>
> **⚠️ 两端归一化边界必须一并断言(四轮补 —— 三轮只断言了 `DZ_INNER < DZ_OUTER` 一端)**:
> 另两条硬上界 **`0 ≤ DZ_INNER`** 与 **`DZ_OUTER ≤ 1`** 此前只在变量表里声明,
> **从未进入任何断言** —— 是两个双向失效口:
> - `DZ_OUTER > 1`:归一化终点在物理行程**之外** ⇒ `t` 永达不到 1 ⇒ **满速永不触发**
>   (反例:`DZ_OUTER = 2, DZ_INNER = 0` **通过**旧断言,玩家推到底也只有半速)。
> - `DZ_INNER < 0`:死区**延伸到物理零点之外** ⇒ 静止时 `t > 0`(反例:`DZ_INNER = −1/2`
>   在 `raw = 0` 静止态给出 **0.35** 的输出 —— 角色**无人操作时自走**)。
> **定死:装载期断言 `0 ≤ DZ_INNER < DZ_OUTER ≤ 1` ∧ `CURVE_POW > 1/2` ∧ `CURVE_POW` 有限**
> 四条并列(承 ADR-014)。**F-3.1 全条无其他机械守门 ⇒ 本断言是它唯一的守门**(见 `AC-3-A9`)。
>
> **Ⓐ `CURVE_POW > 1/2` —— 端点 C1 的充要下界(三轮评审修正)**:
> 初稿写 `> 0` 却同时声称「两端 C1」(见 ②)。**两者不相容** —— 令 `s(t) = 3t² − 2t³`,
> 则 `g = s^P`,在 `t → 0⁺` 处 `s ≈ 3t²` ⇒ `g ≈ 3^P · t^{2P}` ⇒ `g' ≈ 2P·3^P · t^{2P−1}`。
> **`2P − 1 ≤ 0` 时 `g'(0⁺)` 为 ∞ 或非零常数**,而死区外侧的 `out ≡ 0` 斜率为 0
> ⇒ 死区出口处**斜率跳变 = C1 破缺**(正是 ② 要消的折角)。
> ⇒ **`P > 1/2` 是 C1 的充要下界**(`P = 1/2` 亦不满足:此时 `g'(0⁺) = 2·(1/2)·√3 = √3 ≠ 0`)。
> 上界仍归用户;`P` 越大前段越钝,**纯表现偏好**,只在定点下受「前段塌成 0」约束(见上表)。
> **装载期断言**:`CURVE_POW > 1/2` ∧ **有限**(承 ADR-014 区间校验)。
> **双阈值(inner/outer)而非单阈值**:单阈值在边界处**抖动**(轴在阈值上下来回跳 ⇒ 移动顿挫)。

### F-3.2 ~~焦点重复速率~~ —— **整块删除(评审裁决)**

> (`REPEAT_DELAY` / `REPEAT_START` / `REPEAT_STEP` / `REPEAT_MIN`)。

> ① **与官方机制结构冲突** —— Unity Input System 的绑定层**已提供**

### F-3.3 急救延迟预算(`TR-concept-007` 的兑现口径)—— **已重写(评审)**

> **⚠️ 本式初稿是一句恒等式,不具备验收能力 —— 整块重写。**
>
> **初稿原文**为加法分解 `L_input→judge = L_poll + L_axis + L_judge`,
> 再令 `JUDGE_BUDGET := 50 ms − L_render`,判据 `L_input→judge ≤ JUDGE_BUDGET`。
> **代入后与 `L_input→pixel ≤ 50 ms` 代数等价** —— 两个「判据」其实是**同一条**,
> 只是移了项。⇒ 它**不能**独立验收任何东西,也**不能**为「绕过 UI 栈」提供算术理由
> (UI 路由是**帧内调度成本**,不改变 `L_render`,所以「绕过 UI 能腾出预算」是**假的**)。
> **结论对、理由错**:直读通道**保留**,但理由换成下面这条**方差论**。

**真正的判据(单条,回归 `TR-concept-007` 的原话)**

```
判据:L_input→pixel ≤ 50 ms                     ← 唯一硬预算(technical-preferences.md)
     (此式覆盖输入采样 → 判定 → 提交 → 像素点亮 的全链)
```

**直读通道为什么保留 —— 方差,不是均值**

- 杀死「手稳」的不是**平均**延迟,是**抖动(方差)**。玩家在急救动作里练的是
  **可重复的时机感**;一条均值 20 ms 但偶尔抖到 60 ms 的链,**不可练**。
- 经 42 UI 栈的路由,延迟是 `EventSystem` 帧内**调度顺序**的函数:同一帧内
  其他 UI 消费者的顺序、脏布局重算、`InputSystemUIInputModule` 的处理时机
  都会让这一跳的延迟**逐帧变化**。均值可能够低,**方差不可控**。
- 直读(`InputSystem.onAfterUpdate` 回调取值)**把采样点钉死在 `Update` 之前的固定相位**,
  与 UI 栈的帧内调度**解耦** ⇒ 方差主要只剩引擎渲染管线那一项,**可测、可控、可练**。
- ⇒ **通道归属 = 确定性**,不是「省下的毫秒数」。

**分项表(降级为诊断工具,不再作判据)**

| 分项 | 含义 | 归属 | 备注 |
|------|------|------|------|
| `L_poll` | 采样到动作值可见 | 引擎 | 随 `updateMode` 变化;**须实测**,不假设 |
| `L_axis` | F-3.1 曲线求值 | 3 | O(1),可忽略 |
| `L_judge` | 10 的判定求值 | **10** | **纯逻辑、无 I/O、无分配** |
| `L_schedule` | UI 栈帧内调度引入的**抖动** | 42 | **本式新增的可见项** —— 直读通道消灭的就是它 |
| `L_render` | 提交到像素点亮 | 引擎 + 2 | **≈2 帧**(承 F5)—— 占预算主项 |

> **⚠️ `L_render` 单独就可能吃掉全部预算**:60 fps 下 ≈33 ms;若某机型
> `L_render ≥ 50 ms`,则 `L_input→pixel ≤ 50 ms` **在结构上不可满足**,
> **与 3 无关**。**降级路径(评审补,须在最低目标硬件上验证)**:锁定刷新率为 60 Hz + **独占全屏**
> (避开合成器多一帧排队);
> **⚠️ 定性(复审修正)**:这是**节奏 / 一致性**措施,**不是延迟措施** ——
> 在 144 Hz 面板上锁 60 Hz **会抬高**均值延迟;它买到的是**刷新相位的稳定性**(方差),
> 而方差才是杀死「手稳」的东西。**不得当作「降延迟」写进任何报告。**
> 若仍不达标 ⇒ **须重新与用户裁定 `TR-concept-007` 的可行性**,不得假装达标。
>
> **VR 预算更紧(90 fps ⇒ `L_render` ≈22 ms),且 VR 急救动作归 P1b**
> (**权威 = `game-concept.md:723` 范围阶梯**「VR 急救动作 = P1b」)。
> **复审修正(层级引用)**:初稿把 `adr-013` §二 的「VR / world-space 实现推 P1a」
> 当成了「VR 功能 = P1a」—— 那是**world-space UI 栈**的层级,不是 VR **功能**的层级。
> `adr-018` §七 与 `adr-020` §三 沿用了这处误读,**三份 ADR 须同批订正**(登记见 §Dependencies 五)。
> **P0 不验收 VR 延迟** —— 无论 P1a 还是 P1b,VR 都在 P0 之后,故**不影响任何 AC**。
> 初稿把 VR 写进 P0 判据是**层级错位**。

### F-3.4 手感层 / 判定层的分流式(**唯一漏斗 + 仅整数**)

> **用途**:把规则八写成**可机械判定的结构约束**。
> **本式已重写(评审)**:初稿把判定层写成 `FixParse(r)`,**范畴错误** ——
> 见下方修正一。

```
手感层(3):  float v = ReadValue(action)  →  表现(振动 / 曲线 / 提示)  →  【丢弃】
读数层(3):  EmergencyReading b = ReadEmergency(action)   b 的字段全是 int( tick 持时 + 边沿 )
判定层(10): JudgeResult r = Judge(b, ...)                 r 的字段全是 int / Fix
             SimEvent e = new SimEvent(payload: r 的整数字段)   ← 10 直接构造,无解析
             IEventSink.Append(e)                              ← 10 写流;3 的程序集内无此调用
```

| 边界 | 规则 |
|------|------|
| **`float` 允许出现的位置** | 仅 `L_axis`、表现触发、渲染 —— **一律不进流、不入存档** |
| **进流的唯一形态** | `JudgeResult` 的**整数字段**直接拷进 `SimEvent` 载荷(承 ADR-006;**由 10 构造**) |
| **3 ↔ 10 的边界类型** | `EmergencyReading` —— 全整数(tick 持时 + 边沿 + 动作枚举);**不含判定** |
| **唯一字符串→数值入口** | `FixParse.Parse(string)` —— **导入期**用,解析创作态 `"1/8"` 这类比值 |
| **禁止 ①** | 任何 `float` / `double` 字段出现在 `SimEvent` 载荷的**可达类型**里 |
| **禁止 ②** | 运行期调用 **`FixParse.Parse(string)`**(字符串入口,属导入期);`FixParse.FromRatio(long, long)` **不在禁列**(整数入参,无浮点路径);**无第二解析入口**(禁 `(Fix)` 强转字面量) |

> **评审修正一 —— `FixParse.Parse(string)` 是导入期的,不是运行期的**(`adr-006:105-122`)。
> 初稿写 `JudgeResult r = Judge(...) → FixParse(r) → Append(...)`,**不成立**:
> `Parse(string)` 的签名**吃字符串**、且 **ADR-006 明写「运行期不存在从 `float`
> 到 `Fix` 的路径 —— 编译期就不可表达」**。运行期根本**没有** `FixParse(r)` 这个东西可调。
> **正确形态**:`Judge` 的返回类型**本身就全整数**(`int` 计数 + `Fix`),由 **10** 直接构造
> `SimEvent`,**不经任何解析**。解析只发生在**装载创作态 JSON** 时。
>
> **评审修正二 —— 具体存在一条浮点泄漏链(初稿 AC 抓不到)**:
> 若不强制,**会发生**:
> `Emergency = Button(hold)` → **按住时长是 `float` 秒** → 乘**熟练度修正系数**(C5 说是分数)→
> 得出 `JudgeResult` → 填进 `SimEvent`(**全在 10 侧**;3 只交 `EmergencyReading`)。
> **链条每一跳看起来都「只是乘一下」,但终点是 `float` 进流。**
> `AC-3-B3`(断言 `JudgeResult` 全整数)**抓不到结构体字段** —— 它只看顶层类型。
> ⇒ **新增 `AC-3-A7(BLOCKING)`**:在 `SimEvent` 载荷的**可达类型闭包**上不存在
> `float` / `double` 字段(递归扫描,与 `PresentationDtoGuard` 同构的机械形式)。
>
> **修正后的口径(三轮)**:**「3 只出整数读数与意图;判定(`JudgeResult` / `SimEvent`)
> 全归 10;判定结果全整数」**。

### F-3.5 绑重 schema hash(优雅失效的判据)

> **用途**:规则五的判据式。**local-only,不进 sim、不需跨机一致** —— 但**须同机稳定**。
> **本式已重写(评审)**:初稿的元组**漏了 `bindingId` 与三组字符串集合**,
> 且**对「保持结构的重建」完全盲** —— 而那正是它要防的东西(见下方⚠️)。

```
记录 r ∈ R            R = 当前动作资产里全部绑重记录(全部 map,含 UI map —— 见下表)
r = ( mapName,                        ← ★ 指名原始属性:InputActionMap.name
      actionName,                     ← ★ 指名原始属性:InputAction.name
      bindingIndex,                   ← InputBinding 在该 action 内的序号(0 基)
      bindingId,                      ← ★ InputBinding.id(overrides 的持久化键即它)
      name, path, isComposite, isPartOfComposite,   ← ★ 原始属性,非 effective*
      processors[], interactions[], groups[] )      ← ★ 三组字符串集合(原始属性)

规范序列化(长度前缀 + 元素计数,免分隔符歧义与空集歧义):
  canon(r) = Σ over 字段:  len(field_utf8) ‖ field_utf8           ← 每字段前挂字节长度
  集合字段:  count ‖ ( 元素各自 canon 后,按 StringComparer.Ordinal 升序,逐个长度前缀拼接 )
需排序时:  记录间按 canon(r) 的 StringComparer.Ordinal 升序        ← ★ 序数,非文化敏感序

SchemaHash = FNV-1a-64( concat_{r ∈ sort(R)} canon(r) )            ← 在 ulong 上算
```

| 字段 | **须用 `InputBinding` 的原始属性** —— 禁 `effective*` / `override*` |
|------|------|
| `name / path / processors / interactions / groups` | **必须读原始属性**(`binding.path` 等)。**⛔ 禁读 `binding.effectivePath` / `effectiveProcessors` / `effectiveInteractions` / `effectiveGroups`** —— 这些是**引擎已合并 override 后的视图**,读它们等于**把 override 值混进 hash** ⇒ 每次玩家改键都改 hash ⇒ 触发「失配 → 清空」⇒ **改键自我毁灭**(与下方「载荷 = 资产结构」硬禁同一失效,只是通道更隐蔽)。**须写 AC 断言**:`R` 的读点上游**不得出现 `effective*` / `SaveBindingOverridesAsJson`**。 |

| 变量 | 含义 |
|------|------|
| `bindingId` | **overrides 的持久化键是 `id`,不是 `bindingIndex`** —— 初稿漏了它,导致「槽位不变但目标变」被判为「结构未变」 |
| `processors[] / interactions[] / groups[]` | 挂在绑重上的处理器 / 交互 / 分组;**改了它们也会改行为**,初稿完全没哈希 |
| `mapName` **是否含 UI map** | **含** —— **R 覆盖动作资产里的全部 map,UI map 不排除**。理由:UI map 的绑重同样受「重建 ⇒ `id` 变 ⇒ override 静默丢」影响(`AC-3-A1` 已断言**全案恰一个资产、UI 模块引用同一资产**);排除它会让「UI map 改绑」这条路径**没有失配防线**。**代价**:UI map 的绑重改动也会触发 hash 变 —— 但这正是所需(该变化本就是「结构变了」)。 |
| 元素计数前缀 | **每集合前挂 `count`** —— 长度前缀只免「`"ab"+"c"` vs `"a"+"bc"`」的分隔符歧义,**免不了空集歧义**:`groups=[]` 与 `groups=[""]` 在纯长度前缀下**同字节流**(单元素空串 = `len=0`)⇒ 补 `count` 使其可区分 |
| 长度前缀 | 防「`"ab"+"c"` 与 `"a"+"bc"` 撞同一字节流」的分隔符歧义 |
| `StringComparer.Ordinal` | **序数比较**;禁文化敏感序(`InvariantCulture` 仍受 ICU 版本影响 ⇒ 跨机器不稳) |
| `FNV-1a-64` | **自实现的逐位确定哈希**(见下⚠️)。**碰撞概率**:64 位、记录数 N 为量级 `O(10¹)` ⇒ 生日界 ≈ `N²/2⁶⁵` ≈ `10⁻¹⁷`,**远低于**「资产重建」这一被检测事件的频率;**且碰撞的后果是「该变而未变」= 退化为初稿的静默失效**,非崩溃。定级 **RECOMMENDED**(本式 local-only,见下硬纪律)。 |

> **⚠️ 硬纪律 —— 不得用 `string.GetHashCode()` / `object.GetHashCode()` 默认实现**:
> 它们在 .NET Core 上**逐进程随机化**,Unity 各后端行为亦不一。
> 用**自己实现的 FNV-1a-64**(纯整数、逐位确定,**不依赖 BCL 未承诺行为**)。
> **初稿提名的 `SplitMix64` 已撤**(评审):它是 PRNG 混合器,**不是字节流哈希器**,
> 且被 ADR-012 **F7** 点名为「`int64` 溢出 —— Mono 定义性回绕 vs IL2CPP C++ UB」
> 的 BLOCKING spike 项 —— **不该把一个未证实的算子引到一条 local-only 判据里**。
> FNV-1a-64 只做乘与异或,**中间状态必须在 `ulong` 上计算**。
> **⛔ `unchecked` 只管 C# 语言规则,管不到 IL2CPP 生成的 C++**(`adr-012:253-256` **F7**:
> C# `int64` 溢出为**定义性回绕**,生成的 C++ **有符号溢出为 UB**)。初稿「溢出可显式 `unchecked` 定死」
> 是一句**对 C++ 而言为假**的断言 —— 复审已改:
> **定级 = RECOMMENDED,不 blocking**(本式 **local-only、不跨机、不进 sim**,
> 位差无玩家可见后果);**但措辞不得推广**到真正绑定该 spike 的位置
> (ADR-010 校验和 · ADR-012 黄金夹具)—— 那里**必须**用无符号域。
>
> **必须兑现 —— 本式要守的失效是「保持结构的重建」**(评审指出的核心盲区):
> 规则五要防的场景是 **「重新构建资产 ⇒ 所有 `bindingId` 重新生成 ⇒ 已存 overrides
> 静默失配丢失」**。而**仅哈希结构**的初稿:重建后 `mapId/actionId/path/...` 全一样
> ⇒ **hash 不变** ⇒ 判定「匹配」⇒ overrides **仍然静默丢失**。
> **即:初稿的判据对它所声明的失效完全盲。**
> **修正**:把 `bindingId` 纳入元组(它在重建后变化)⇒ hash 变 ⇒ 触发失效路径。
> **修正后的不变量(本条的真正内容)**:
> - **增删改 `overrides` 记录不得改变 hash** —— 否则每次玩家改键都触发一次
>   「失配 → 清空」,**改键功能自我毁灭**;
> - **槽位签名的任何改变(含 `bindingId`)必须改变 hash** —— 否则重建后静默丢 overrides。
>
> **载荷 = 动作资产的结构本身**:**R = 从动作资产读出的全部绑重记录**(读**资产**,不读 overrides)。
> **`overrides` 的载荷被结构性排除在哈希之外** —— 这正是 F-3.5 不变量①所需的性质。
>
> **⛔ 硬禁 —— 不得以 `SaveBindingOverridesAsJson()` 的载荷为记录集合**(复审裁定,本式最危险的一处):
> 该 API 返回的是 **override 差分**,且**携带绑定值**(`path` / `processors` / `interactions` / `groups`)。
> 以它为 `R` 会同时踩两条线:
> ① **含绑定值** ⇒ 玩家每次改键都改 hash ⇒ 触发「失配 → 备份 + 载入默认」⇒ **改键自我毁灭**
> (违反 F-3.5 不变量①;亦违反用户裁定「含 `bindingId`,**不含绑定值**」);
> ② **载入期 `RemoveAllBindingOverrides()` 已把载荷清空** ⇒ 重算出的 hash 是**空集**的 hash
> ⇒ **每次启动都失配** ⇒ 全部改键静默丢失(比①更坏:不是偶发,是必现)。
> **`R` 的唯一来源是资产结构**(F-3.5 代码块的 `R` 定义本就是如此)。**不自建第二套序列化**(与规则四的工厂口径同源)。

## Edge Cases

> 每条格式:**情形 → 3 做什么 → 谁不做**。凡涉及写 sim 的,一律**不在 3**。

### 一、设备与系统级中断

| 情形 | 3 的行为 |
|------|---------|
| **手柄在急救中途断连** | **合成 release**(所有 `IsPressed` 转 false)+ 直读通道进 `Suspended`;**不冻结帧**;10 侧按「动作被打断」处理(归 10) |
| **系统级失焦**(Alt+Tab / 头显取下) | 同上:合成 release + `Suspended`;**这一条防的是「卡键」** —— 失焦时按住的方向键在回到游戏后**永远按住**,是最经典的致命 bug |
| **设备热插拔(非急救期)** | 重算设备态(§States 一);`QueryBinding` 的 `device` 随之更新,42 / 48 刷新图标 |
| **`NoDevice` 且无存档可改键** | 玩家**无法操作** —— 这不是 3 能解决的(无改键 UI);**记为已知 P0 限制**,见 `OQ-3-1` |

### 二、绑重与资产

| 情形 | 3 的行为 |
|------|---------|
| **动作资产被重建(GUID 全变)** | schema hash 失配 → **优雅清空**(旧文件改名备份 + 载入默认 + 记日志)。**不静默采用错位 overrides** |
| **玩家改键后游戏升级(结构未变、绑定值变)** | hash **不变** ⇒ overrides **保留**。**这是正确的** —— 玩家的改键不该因版本升级丢失 |
| **overrides 文件损坏 / 半截** | 视同失配:备份 + 载入默认。**不尝试部分恢复**(半个文件的语义未定义) |
| **只读目录 / 磁盘满(写 overrides 失败)** | **记日志 + 本次会话内仍生效**(内存态),下次启动回退默认。**不静默失败** |
| **未有 overrides(首次启动)** | 载入资产默认绑定。**这是正常路径,不是异常** |

### 三、导航与焦点

| 情形 | 3 的行为 | 谁负责 |

| **键鼠与手柄同时输入** | 设备态 = `Mixed`,**以最近一次有效输入来源为准**(§States 一)—— **不双活** | 3 |
| **同一动作被绑到两个物理输入** | **合法**(如 `Interact` 同时绑 `E` 与手柄 `South`)—— 这是**绑定**,不是**双触发** | 3 |
| **同一动作同时绑官方桥与自实现路径** | **不适用(三轮)**:3 侧**不存在**自实现路径(规则十一 + `AC-3-C4`)—— 单一真源 = 官方桥。`AC-3-C2` 现为**结构性构造断言**(喂 `Navigate` 的控件不得喂第二个焦点动作) | 3 守门 |

### 四、无改键 UI 的后果(**本 GDD 明写的已知限制**)

> **P0 玩家无法改键**(用户裁定①)。这不是「暂时没做」,是**排期决定**。诚实记账:

| 后果 | 严重度 | 缓解 |
|------|--------|------|
| 手柄布局不理想时只能忍 | 中 | 默认三套绑重**须按主流布局**,标准越高越好(3 的唯一缓解手段) |
| 无障碍改键需求(49)在 P0 无出口 | 中 | `OQ-3-1`;机制已备,补界面即可(不是返工) |
| 键位提示错误时玩家无法自救 | 低 | 无提示浮层(依据 = `technical-preferences.md:33` + `AC-8-43/44`,**非支柱五**)⇒ **不存在「提示错了」这个状态** |

### 五、联机(承 F1)

### 一、轴处理(F-3.1 —— 手感层)

| 旋钮 | 作用 | 安全范围 | 破了会怎样 |
|------|------|---------|-----------|
| `DZ_INNER` | 漂移忽略门槛 | `0 ≤ · < DZ_OUTER ≤ 1` | 太大 → 推到底不满速 |
| `DZ_OUTER` | 归一化终点 | **`DZ_INNER < · ≤ 1`**(**≤ 1 是硬上界** —— `m` 已归一,`· > 1` 使满速永不可达) | 太大 → **满速永不触发**(推到物理极限仍 `t < 1` ⇒ 走不满);太小 → 曲线陡到不可微调 |
| `CURVE_POW` | 响应曲线指数 | **`> 1/2`**,上限待用户定(建议 `≤ 3`) | 见 F-3.1 表 · Ⓐ(`≤ 1/2` ⇒ 端点 C1 破缺);归 1 / 2 手调 |

> `DZ_OUTER ≤ 1`(否则满速永不触发)· **`CURVE_POW > 1/2`**(端点 C1,见 F-3.1 Ⓐ)。

### 一之二、设备态切换(§States 一 · `AC-3-D4` —— `Mixed` 的迟滞)

> **复审补**:初稿把 `DEVICE_SWITCH_THRESHOLD` 写进 `AC-3-D4` 却**未列入本表** ——
> 一条**无值、无型、无范围的孤儿旋钮**(且另有二参数完全未命名)。本节补死。

| 旋钮 | 作用 | 安全范围 | 破了会怎样 |
|------|------|---------|-----------|
| `DEVICE_SWITCH_THRESHOLD` | 夺源所需的**持续位移**门槛 | **`0 < · < 1`(两端都不可取)**;**比较域 = 径向幅度 `‖Δ‖`**(见下方 Ⓑ) | `= 0` → 迟滞消失,漂移即夺源(初稿的抖动复活);**`≥ 1` → 任何轴都到不了**(轴值 ≤ 1)⇒ **永远锁在首个被看见的设备**,`Mixed` 名存实亡 |
| `DRIFT_TOLERANCE` | 静止期**漂移容忍带**(须先超出它才计入夺源) | `> 0`,**建议 ≤ `DZ_INNER`**;同**径向**域 | 太大 → 轻推也夺源;太小 → 手抖即夺源;> `DZ_INNER` 会留下「已出死区却仍算漂移」的空隙 |
该 tick 数的秒级体感(「持续多久才算位移」)曾依赖 tick 频率标定 —— ✅ **已解除(✅ 已标定 2026-09-20:20 Hz ⇒ 1 tick = 50 ms · 在场才模拟 · CAP=24)** —— `BLOCKED-BY` 撤除,值仍归用户

> **Ⓑ 比较域必须写死 = 径向(三轮评审修正)** —— 初稿只说「超过门槛」,**未定这与什么比**:
> 逐分量(任一轴超阈)还是径向(合矢量超阈)?两条在斜向输入下**判据不同**
> ⇒ 实现者各自拍定 ⇒ `AC-3-D4` 不可签核。
> **定死:`‖Δ‖` 径向,与 F-3.1 同域、同 `‖·‖₂`** —— 逐分量判定会在斜向**过早**夺源
> (单轴 0.7 即触发,合矢量已 0.99),与 F-3.1 的「逐向等速」纪律**同源**。
>
> **Ⓑ.1 设备侧列数(鼠标侧单列)** —— **鼠标无轴**,其「位移」是**指针增量**(`Vector2` delta);
> 摇杆 / 触控板是**轴值**(归一化 `[-1,1]²`)。**两侧量纲不同,不可同一阈值直接比**:
> **定死 = 鼠标侧取单列 `‖pointer_delta‖`(逐帧增量模长,不含方向),独立于轴的归一化域**;
> 即本旋钮在**鼠标侧按「指针位移」语义解释、在轴设备侧按「轴幅度」语义解释**,
> **两列各自成表**(`DRIFT_TOLERANCE` / `DWELL_DURATION` 亦各有一列)——
> ADR-014 的常量表须**按设备类分别登记**,不得共用一行。**由 ADR-014 落盘时体现。**

### 一之三、输入系统更新模式(规则七 · `AC-3-B2` —— 三轮补登记)

> **三轮补**:**`InputSystem.settings.updateMode` 是初稿的第二个孤儿旋钮** ——
> 它被两条正文点名(规则七「必须钉死并实测」· §三 `L_poll` 行「随 `updateMode` 变化」),
> 却**从未进任何旋钮表**,也**没有值 / 型 / 范围**。同一类错误(`DEVICE_SWITCH_THRESHOLD` 孤儿)
> 已在复审时修过一次 —— 这是**同构复发的第二例**。

| 旋钮 | 作用 | 取值(枚举) | 为什么 |
|------|------|-----------|--------|
| `INPUT_UPDATE_MODE` | 决定 `InputSystem.Update()` 在播放循环中的**相位** —— 直接改变 `L_poll` 与**采样频率** | **枚举三值:`Dynamic`(默认)/ `Fixed` / `Manual`**;**本项目须钉死 = `Dynamic`** ⚠️ **须 spike**(见下) | **`Dynamic`**:输入在 `Update` 相位更新,与 `onAfterUpdate` 回调**同相** ⇒ 采样频率 = 渲染帧率,**每帧恰一次**。**`Fixed`**:输入随 `FixedUpdate` 更新(默认 50 Hz 物理步长)⇒ 帧率 ≠ 采样率,**同一渲染帧可能吃到 0 或 2 次输入更新** ⇒ **引入与帧率耦合的抖动**(正是规则七「方差论」要消的东西)。**`Manual`**:须 3 自行调 `InputSystem.Update()`,把播放循环控制权揽进输入层 ⇒ 与引擎其余部分竞争的隐式契约,且 `onAfterUpdate` 相位不再是引擎保证的。 |

> **⚠️ 符号可信度分层(四轮 · 用户裁定①「分层处置」)** —— 上表的**符号名**
> (`InputSystem.settings.updateMode` 与三个**枚举成员名** `Dynamic` / `Fixed` / `Manual`)
> **在引擎参考库中零覆盖**(`docs/engine-reference/unity/modules/input.md` 356 行只覆盖
> `SaveBindingOverridesAsJson` / `LoadBindingOverridesFromJson`,`:269-274`)。
> 按本项目纪律分层处置:
> - **① 判据层(BLOCKING AC)零未核验符号** —— `AC-3-B2③` 的判据**不引用枚举成员名**,
>   只断言**性质**:「输入更新**相位 = 渲染帧相位,且每帧恰一次**」。理由 = 本文件 `AC-3-A4`
>   自订的同一纪律(「把存在性未经仓内核验的符号写进 BLOCKING AC 会造出**一条不可编译的验收**,
>   比没有更坏」)—— **同一条命题在 A4 已正确应用,四轮 sweep 发现 B2③ 未同步**。
> - **② 规则 / 实现指引层保留符号名** + 本处**「须 spike」标记**,并汇总到唯一 spike 册页
>   (`adr-011` §Risks,见 §Dependencies 五)。
> - **③ 降级路径** —— 若 spike 证明该 API 形状不同(改名 / 改型 / 不存在),**承载的性质不变**:
>   判据改为「每渲染帧输入恰被更新一次」,**不依赖任何具体 API 形状**。
> **装机 / 启动期断言为「性质断言」**(非配置项);若因故须改,走一次 ADR 修订并重做 `AC-3-B1b` 实测,
> **不得静默改**。**枚举非数值** ⇒ 不走 ADR-014 的比值化路径(`FromRatio` 只收整数),
> 但**仍须登记**(「存在且落在此处」是 3 的所有权,见本节表头)。
> **`AC-3-B2③` 守门**(见 Acceptance Criteria)—— 该 AC 现同时守「不穿过 UI 栈」与「更新相位性质」。

  (改 `path`),断言:重算 hash **不变**(若读点用了 `effectivePath` 或 override 载荷,**必变** ⇒ 抓出)。
  **⑥ sidecar 字节往返** —— `Save…` 写出的 overrides 文件**逐字节**喂 `Load…`(3 不解析、不重写);
  断言「喂入字节 == 保存字节」。
  **⑦ 集合元素计数前缀生效(四轮补 —— I1 唯一的软点)** —— 构造两个**元素数相同但切分不同**的集合
  (测试夹具:`groups = []` 与 `groups = [""]`),断言二者 hash **不同**。
  **理由**:I1 的「每集合前置元素计数」子句此前**无专项用例**,若实现漏写计数前缀,
  `["a","b"]` 与 `["ab"]` 会撞 hash 而**所有既有用例仍通过** —— 本子句正是补这个盲区。
  ①②③⑤⑥⑦ 为 EditMode 测试。
- **AC-3-E4(BLOCKING · 新增)** —— **`Idle` 期零成本是真的**:`Idle` 态断言
  `Emergency` 动作 `enabled == false`,且**读取回调调用次数 == 0**。
  **本条直接回应初稿「不在急救时零成本」的错误断言** —— 已 enable 的 action
  **每帧都被 `InputSystem.Update()` 更新**,与是否 `ReadValue` 无关(§States 二 修正注)。
- **AC-3-E5(BLOCKING · 新增)** —— **`Armed` 读取路径零分配**:读取回调内
  **`GC.Alloc == 0`**。初稿声称零成本却**无分配判据** —— 而回调路径恰恰是闭包 / 装箱最容易漏的地方。
  **方法学四要素须在测试报告中明写(三轮补 —— 与 `AC-3-B1b` 同纪律,缺一不可)**:
  ① **统计量 / 阈值** = 分配**字节数**上界 `0`(不是「平均」—— 一次分配即失败);
  ② **采样窗口** = 连续 **≥ N 帧**(N 由用户在最低目标硬件定稿时拍定)的 **`Armed` 全程**;
  ③ **剔除规则** = 显式**预热帧**(`# of warmup frames` 由用户定)后开始计数 —— 否则首次 JIT / 池化分配
  会把稳态误判为分配;
  ④ **采集工具** = 分配探针(建议 `ProfilerRecorder` 对 `GC.Alloc`;**须在 Development Build 下测**,
  `GC.Alloc` 计数在非 Development Build 中不可用)。**探针口径须同时跑 Mono 与 IL2CPP 两后端**
  (分配行为不同)。**具体数值(N / 预热帧数)由用户拍定** —— 3 不替用户定值。
  **扩展(三轮补):`Armed` 之外,常驻轴路径亦须零分配** —— `Move` / `Look` 的逐帧读取
  (含 F-3.1 的 `Fix → float` 转换,见 §Debt 中「`Fix → float` 读路径」一条)**每帧都在跑**,
  分配影响面比 `Armed`(短窗)更大;本 AC 的子句 ⑤ = **非急救帧的常驻轴读路径 `GC.Alloc == 0`**
  (同四要素口径)。
