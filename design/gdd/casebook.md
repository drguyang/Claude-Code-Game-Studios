## Summary

39 是**那本纸**。它拥有脉案的**布局、持久化与所有权**,以及**每玩家一本的分册**。

**39 不诊断、不结算、不渲染** —— 它把 8 给的**词与形态**、37 给的**病例生命周期**,
装订成一页玩家可以用笔写、可以用手翻的纸。**玩家在这里做的唯一事情是落笔与结案**
——而这两件事都**没有对错反馈**(8 铁律① · 37 规则九)。

**39 是支柱四的**呈现**载体**:三案链之所以成立,是因为玩家能**把纸摆在一起看**。
(⭑ 2026-09-19:37 是机制载体 =「P0 唯一载体」;39 是呈现载体 —— 两处措辞不再互撞。)

## Overview

39 是**「分册态」的持有者 —— 三流之外的第四类数据**(⭑ 2026-09-19 首轮评审 · 用户裁定 C 路:
39 从「呈现层第三件套」**升格为分册态层**,见下)。它的身份句是**「拥有持久化与分册的呈现系统」**,
不是纯渲染器:它持有的 tick / 痕 / 分册 **不进三流**,但**必须跨存档**,故在 ADR-010 的
存档布局中**新增一个槽位**(分册态段,见架构依赖)。**39 与 42 / 44 不同构** ——
42 / 44 是「只渲染 / 只读」件套,39 是**唯一的「带持久化的呈现系统」**(用户裁定,2026-09-19)。

> **⭑ 层籍裁定(2026-09-19 首轮评审 · 用户裁定 [C] 升格为分册态层)**:39 持有「两个 tick + 痕 + 分册」
> 三项影响诊断 / 结算的**邻接派生态**,却自称呈现层第三件套 —— 身份句与职责句同文档对撞
> (BL-1 / BL-3 根因)。裁定:39 **正式登记为三流之外第四类数据(分册态)的持有者**;
> ADR-010 §三 义务表**补 39 行**、§一 布局**补「分册态段」槽**;7a 存档布局随之改。
> 代价最大但**唯一能回答「重载后『旧』态还在不在」**(存 = 在)。

**边界是三层,必须物理分开**(承 `diagnosis-system.md` UI-8.0):

| 层 | 拥有什么 | 不拥有 |
| --- | --- | --- |
| **8 诊断** | 体征**词** · 精度档 → 呈现**形态**的映射 · 四态规则 · 病名栏与置信度的**形态** · **焦点顺序语义** | 渲染、持久化、布局像素 |
| **37 病例** | 病例**生命周期** · 判断记录的存档(病例流) | 状态机转移规则 |
| **39 脉案** | 脉案页的**布局** · **分册态持久化**(两个 tick · 痕 · 分册) · 病例列表的**呈现组织** | 词从哪来、什么档给什么词、生命周期;**不写三流** |
| **42 拟物 UI** | **渲染**与**焦点导航**的引擎实现 | 游戏状态 |

> **⚠️ 39 的独有职责是「持久化」与「分册」。** 8 的「旧态」判定需要**三个时刻**中的两个
> (快照 tick / 上次重查 tick),而 8 **铁律③ 不持任何持久化** ⇒ **这两个 tick 住 39**
> (`diagnosis-system.md:785`)。同理,联机下**每人一本**(D-8-10 / 铁律⑤),**分册键 = `player_id`**
> —— 也是 39 的职责。**这三项(两个 tick · 痕 · 分册)构成「分册态」** —— 三流之外的第四类数据,
> **必须跨存档**(⭑ 2026-09-19 用户裁定 C 路,ADR-010 补槽)。

## Player Fantasy

**「这是我的本子。上面有我的字。」**

- **纸的物理性** —— 翻开有纸纹,写字有压痕,划掉有划痕。承 42 的 USS 元件库
  (纸纹 / 墨迹 / 卷轴九宫格)。
- **字是我的** —— 病名是**你写下的**,不是系统给的。体征行是**系统写的**(查体产生);
  两者笔迹同源(都是「我的手」),但**空间上分栏**(承 UI-8.1 铁律③)。
- **本子是我的** —— **联机下每人一本**(D-8-10)。你的读数、病名、置信度、改写痕**都不共享**,
  但**同一病人的客观体征对四人是同一个真值**(`diagnosis-system.md:833`)。

> **⚠️ 39 的幻想主通道是「翻」。** 三案链的全部力量在于**玩家自己把纸翻到一起** ——
> 所以 **39 绝不替玩家做归纳**(AC-39-08)。**归纳是玩家的动作,不是界面的功能。**

> **⭑ 支柱四载体措辞(2026-09-19 首轮评审修订)**:39 自称「支柱四的物理载体」,而 37 自称
> 「该图样的 P0 **唯一**载体」(`case-system.md:30`)。两处不能都是「唯一」—— 37 是**机制**载体
> (识别 / 结算发生在 37),39 是**呈现**载体(纸让玩家看得到图样)。**措辞收窄:37 是「唯一」,39 是「呈现载体」。**

## Detailed Rules

### 规则一:39 拥有分册态,8 / 37 拥有规则与生命周期

| 面 | 归属 | 依据 |
| --- | --- | --- |
| **体征词 / 未查标记 / 病名栏与置信度的形态** | **8** | UI-8.0 · 8 出向表 |
| **焦点顺序语义**(面色 → 语声 → 姿态 → 呼吸 → 触感 → 病名 → 置信度) | **8** | UI-8.2 |
| **病例生命周期 / 结算** | **37** | `case-system.md` 规则一 |
| **脉案页的布局与分册态持久化** | **39** | UI-8.0 · `case-system.md:403` · ⭑ 2026-09-19 层籍裁定 C |
| **三个时刻中的两个**(快照 tick / 上次重查 tick) | **39** | `diagnosis-system.md:785` |
| **渲染 / 焦点引擎实现** | **42** | ADR-013 §三 |

> **⭑ 2026-09-19:39 的「持久化」不是「游戏状态」**(42 铁律的禁区),而是**分册态** ——
> 三流之外的第四类数据,ADR-010 存档布局新增「分册态段」承载。**39 不写三流**(`IEventSink` 零调用),
> 但它的分册态**影响诊断**(tick → 8 的「旧」态)与**结算**(分册 → 37 按各自分册计)—— 所以它**必须跨存档**。

### 规则二:每玩家一本,分册键 = `player_id`(⭑ 2026-09-19:契约 + 作者轴 + 派生语义)

**1–4 人联机下,每个玩家拥有自己的脉案。** 读数、病名、置信度、改写痕**均不共享**。

- **分册键 = `player_id`**(D-8-10 · `diagnosis-system.md:1115`)。
- **客观体征是共享真值**:同一病人的**客观体征**对四人是**同一个真值**(真值归 9/8,
  `diagnosis-system.md:833` / `:1163`);**分叉的只有玩家自己写下的东西**(规则二)。
- **37 结算时按各自的分册计**(`diagnosis-system.md:835`)。
- **单人下分册退化为单册** —— 同一代码路径,不给特例(`player_id = 0`)。

> **⭑ `player_id` 契约(2026-09-19 用户裁定 [A] 本轮只登记契约,机制归 45)**:`player_id`
> 全库零定义、无发号权威(主评审 BL-2;48 的 `AC-48-09` 同病)。**本 GDD 本轮只登记契约**:
> ① 分册键 `player_id` 须在**加入 / 离开 / 主机迁移**下**稳定且不复用**(禁止槽号复用导致串册);
> ② 发号机制归 **45 网络层**(GDD 轮),与 ADR-001 窄修订(意图上行通道)同批;
> ③ ~~P0 单机 = 常量 `0`,不进高水位扫描(承 ADR-007 §四 哨兵纪律)~~。
> **⚠️ 2026-09-21 第二十七批口径订正(承 ADR-006 Amendment B 注记 · 用户裁定 = 复用 `IIdAuthority`)**:
> 单机玩家 id **亦走发号**(建世界时由主机经 `IIdAuthority` 铸造,与 patient / 敌人共用同一 id
> 空间 + 同一条 `max(id)+1` 高水位重构路径),**非常量 0**;`0` 是合法发号值、非哨兵 ——
> 哨兵仍仅 `PatientId.None = −1`(ADR-007 §四)。registry 落点 = `entities.yaml`
> `next_player_id`(契约面 ①② 不变;`TR-casebook-002` 残 ② 45 铸造契约仍 open)。
> **AC-39-04 ③ 即本契约的 39 侧判据;48 侧须同步登记同类契约。**

> **⭑ 判断的作者轴(2026-09-19 用户裁定 [A] ADR-008 窄修订)**:`JudgmentRecorded` / `JudgmentRevised`
> 载荷**补 `author_player_id`**(ADR-008 修订提案,归 37 / 45 的 GDD 轮同批);
> 判定取法随之改判为 **`J(c,p) = 病例流中该案最后一条作者 = p 的判断事件`**(按作者分轴)。
> **痕 = 病例流(按作者过滤)的读时投影**,不再独立存储 —— 见 F-39.2。
> **有界性**:病例流事件量 × 玩家数(≤4)常数倍,须在 ADR-008 修订中重证。

> **⚠️ 分册是 39 的分册态职责,不是 8 的。** 8 只出**形态**,不持有分册。

### 规则三:病例列表 —— 组织规则归 37,排序键固定

**列表 = 案件的纸页(已开 / 已结)。** 组织规则:

| 项 | 值 | 归属 |
| --- | --- | --- |
| **展示排序键** | `(patient_id, CaseOpened 的 (Tick, Seq))` | **37**(`case-system.md:206` / `:403`) |
| **串接组**(同 `patient_id`) | **线订成叠**(显式串成一组) | 37 定串接键;39 定「叠」的呈现 |
| **状态** | 开 / 结(37 的两态,无第三条边) | 37 |
| **结案页「已处置」勾选** | **UI 仪式,不产生独立事件** | 37 定语义;39 定形态 |

**串接 ≠ 合并**(`case-system.md:207`):每一例**各有各的病名栏** ——
《他回来了》第二幕那一格是**新的空格**(承 UI-8.1 病名栏可空置)。

> **「线订成叠」是 39 的呈现决定,不是 37 的语义扩展** —— 37 给「这些同 `patient_id`」,
> 39 决定它**看起来像一叠装订的纸**。**这是拟物层的自由,不新增机制。**

### 规则四:硬约束 —— 三条「绝不」

承 37 的规则九 与 8 的反幻想:

1. **绝不**显示「未结 N 例」计数 / 红点 / 到期提醒(**反幻想一**;`case-system.md:947`)。
   **列表不是待办清单。** 病例「开着」是**合法终态**,不是「未完成」。
2. **绝不**允许按**病种**分组 / 排序 / 检索(`AC-37-15` / `AC-37-24`)。
   **分组行为的结果就是归纳** —— 那是绕过 `disease_id` 守卫的**间接泄漏路径**。
3. **绝不**呈现任何「此案与某案同源」的提示(`AC-37-16`)。

> **⚠️ 39 是这三条的落点** —— 37 侧的类型层静默(`disease_id` 不进 DTO)由
> **AC-37-15 的递归扫描**守住;**39 侧的排序 / 分组 / 检索能力**由本节 + AC-39-05/06 守住。
> **两者缺一,泄漏面就打开。**

### 规则六:落笔 = 一个公开的物理动作(7a 锚点 ① · ⭑ 联机走 ADR-001 意图通道)

**玩家在脉案上落笔写定病名,是 7a 事件触发 checkpoint 的锚点 ①**
(`EVENT_CHECKPOINT_ANCHORS` = `{脉案落笔 · 病例结案 · 出诊启动}`)。

- **39 触发的钩子** = 「**值得锚点的叙事事件**」的**观察点**;
- **7a 只出观察钩子形状**,39 **不新增任何存档逻辑**(承 `diagnosis-system.md` UI-8.0 补记);
- **持久化承载归 39(分册态)**,**存档时机归 7a**。

> **为什么落笔值得锚点**:落笔是**判断的可回滚边界** —— 7a 的规则十四保证
> 「手动槽永远在**最后一个叙事事件之后**」,落笔是其中之一。**39 提供这个边界,不定义它。**

> **⭑ 联机落笔 = 判定输入,走意图通道(2026-09-19 · BL-8)**:落笔 / 改写**必须进病例流**
> (产 `JudgmentRecorded` / `JudgmentRevised`),而 `IReplayPipe.Publish` **主机单向**、全案无
> **client→host 意图通道**。这是 ADR-001 缺口(`OQ-10-9` / `OQ-4-10` / 系统 20 BL-4)的**第四例**。
> **39 侧登记为本系统的前置依赖**:落笔请求经意图通道上行 → 主机 `Append` + 发号 `Seq`
> (与 10 急救的 `EmergencyAttempt` 同构)。**P0 单机不阻塞**(本地直写);联机实现归
> **ADR-001 窄修订**(与 `OQ-10-9` 同批,45 的 GDD 轮,P1b 前)。

### 规则七:无指针焦点导航(实现归 42,语义归 8,顺序不可变)

承 `technical-preferences.md`(拟物 UI 必须同时支持键鼠与手柄)。39 侧的责任:| 需求 | 39 做什么 |
| --- | --- |
| **焦点顺序** | **不重排** —— 严格按 8 给的 `面色 → 语声 → 姿态 → 呼吸 → 触感 → 病名 → 置信度` |
| **已查行是否重排** | **绝不** —— 重排会让肌肉记忆失效(UI-8.2) |
| **空行** | **必须可聚焦**,有反馈(**压痕声 / 行高亮**),**零提示文案** |
| **不可用动作** | **P0 无** —— 四法出生自带,故**不存在灰掉的按钮**(UI-8.2;这也是一条无障碍红利) |
| **「旧」态的手柄可读性** | 页边**铅笔小勾**(不靠颜色) |

> **焦点单栈门**(ADR-013 §三):同一时刻**仅一栈接收导航意图流**。脉案打开时,世界栈的焦点冻结。
> **禁双 EventSystem**(ADR-013)。

### 规则八:无按键提示(`AC-8-44` / `AC-3-F1a` 的落点)

**脉案必须在零按键提示浮层的前提下,用手柄单机完成诊断**(`AC-8-44`)。

- **绝不**显示「按 X 打开脉案」/「按 A 落笔」的**持久 HUD / 浮层 / QTE 提示条**;
- **教按键是 48 教学的职责**(环境叙事:口述 / 示范 / 纸上的图);
- **3 只提供 `iconKey`**,不承担本门(`input-system.md:806`)。

> **📌 39 与 42 / 48 的联合 BLOCKING**:`AC-3-F1a` 的**手柄单机走查对象**是
> **脉案(39)** —— 39 的布局若依赖 hover / 指针,该 AC 直接失败。**39 是本门的第一责任人。**

## Formulas

> **39 不产生任何数值。** 它是呈现系统 —— 公式只有**排序**与**分册**两条,全 `int`,零 `Fix`。

### F-39.1 病例列表排序(纯函数,零存储)

```
SortKey(c) = ( c.patient_id, Tick(CaseOpened(c)), Seq(CaseOpened(c)) )
OrderedList(p) = sort_asc( { c : c ∈ CasesOf(p) } , by SortKey )
```

| 变量 | 类型 | 来源 | 说明 |
| --- | --- | --- | --- |
| `CasesOf(p)` | 集合 | 37 的 `CasesOf` | **39 不持有病例集** —— 现查 37(⭑ 2026-09-19:`CasesOf` 须在 37 侧登记具名接口,见 §Dependencies 注①) |
| `SortKey(c)` | `(int, int, int)` | 37 | **串接键 = 首分量**;后两分量 = 展示序 |
| `OrderedList(p)` | 序列 | — | `p` = 分册键(`player_id`) |

> **零存储(⭑ 2026-09-19 收窄到「排序」)**:**排序**是**读时计算**,**排序键本身不落盘** ——
> 落盘会造出第二真源(承 ADR-009 §一 Q1 判据)。**这不与 F-39.2 的「痕 / tick 由分册态存」互斥**:
> 零落盘**只指排序计算**,分册态(两个 tick · 痕 · 分册)是**另一个存储面**。

### F-39.2 分册键(⭑ 2026-09-19:痕 = 病例流读时投影,不再独立存储)

```
VolumeKey(p) = p.player_id
Page(p, c)   = ( VolumeKey(p), SortKey(c) )      // 页的稳定标识
Traces(p, c) = { e ∈ JudgmentRevised(c) : e.author_player_id = p }   // ⭑ 读时投影
```

| 变量 | 说明 |
| --- | --- |
| `VolumeKey(p)` | **联机分册键**(规则二);单人下为常量 0 |
| `Page(p, c)` | 页标识 —— **用于改写痕的归属**,不入病例流(痕是**分册态派生**,见 §UI) |
| `Traces(p, c)` | **改写痕 = 病例流中该案所有 `JudgmentRevised` 按作者过滤的投影** —— **零独立存储** |

> **⭑ 痕的去向(2026-09-19 · BL-4 裁定)**:改写史已被 37 规则四 + ADR-008 事件化
> (`JudgmentRevised`,全序按作者分轴取法 `J(c,p)`,见规则二)。**痕 ≠ 第二份账**:
> 39 侧只可能是**病例流的读时投影**(与 F-39.1「排序零存储」同一条纪律 —— 投影是派生态)。
> **前提 = 判断事件带 `author_player_id`**(ADR-008 修订,规则二)。**「痕的存储由 39 承担」一句已删。**
> 承 8 的 S-8.3 性质 2:「**痕是给玩家自己看的,不是给系统的评分输入**」
> —— **`#53` 结算时不得因改写次数扣分**(判据 = `AC-37-20`,闭集 = 53 的入向契约,**39 不复述**)。
> **且绝不进 `CaseClosed` 载荷**。

> **⭑ 2026-09-19 修订(F-39.1 注)**:39 的存储面**只有一个** —— 分册态段(两个 tick · 分册)。
> 排序与痕都是**读时计算**。原稿「39 拥有持久化」与「F-39.1 零存储」读作矛盾,实为两义:
> **零存储 = 排序计算不落盘;持久化 = 分册态必须跨存档。** 二者不互斥。

## Visual/Audio Requirements
