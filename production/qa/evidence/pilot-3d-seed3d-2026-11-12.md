## 5 清理轮做了什么 / 没做什么

**做了**(全部机械、可复跑):

1. glTF 导入后 `parent_clear(CLEAR_KEEP_TRANSFORM)` + 烘旋转/缩放 —— 消除父级倍率;
2. `remove_doubles(1e-5)` 合并 UV 接缝处的分裂顶点;

4. 非流形边(>2 面)逐条删除其**面积最小**的面(上限 50 次);

## 8 本轮抓到的三个测量陷阱(可复用)

1. **父级缩放**:glTF 导入挂着父级空物体,`obj.dimensions` 与本地 scale 差一个倍率
   ⇒ 帐篷首次输出尺寸**恰好是目标的一半**。修法:`parent_clear(KEEP_TRANSFORM)` + 先烘变换再量。
2. **非流形边假零**:重新 import 导出的 glb 直接数,得到 **0**;合并顶点后仍是 **3**。
   glTF 按 primitive 重拆顶点,不合并就永远数不出。判据口径 = **合并后**。
3. **UV 重叠指标作废**:首版按「重心 + 三边中点落栅格、同格多面即重叠」测得 0.666 ——
   该值测的是**面密度**,相邻面必然共享边/角;密网格恒高。已删,改记 NOT-RUN。

**另有一条修复经验**:`dissolve_degenerate(dist=1e-3)` 会把 7 万面一起溶掉并**新造 75 条**
非流形边 ⇒ 已弃用,改为「逐条删最小面」(实测 2 面即可清零)。

## 12 Unity 导入实测(2026-11-12 · 帐篷 500k 面)

**为什么补这一节**:§8.10.6.9 判的是「清理后」,但真正决定这些资产能不能进 P0 的是
**引擎侧成本**。渲染图不能回答这个问题。

**方法**:glb → Blender 导出 **FBX + 两张 4096² PNG**(工程无 glTF 导入包,`manifest.json` 零命中);
放入临时目录 `unity/Assets/_PerfProbe/`,用 `PerfProbe.Run` 测 **冷导入**
(源文件挪出 Assets → `Refresh` 清缓存 → 挪回 → 计时 `ImportAsset`)。

> ⚠️ 冷导入**不能**用 `AssetDatabase.DeleteAsset` —— 它删的是**源文件本身**。首版这样做,
> 得到 `import_ms=0` + `no gameobject`(文件已不存在)。这两个数看起来像"导入飞快",实际是"没东西可导"。

| 指标 | 实测 |
|---|---|
| 冷导入耗时 | **3,312 ms / 件** |
| 顶点(Unity 侧) | **344,264**(Blender 侧 249,932 ⇒ **FBX 按法线/UV 拆点 +38%**) |
| 三角面 / 子网格 | 499,990 / 1 |
| 网格运行时内存(`GetRuntimeMemorySizeLong`) | **43.0 MB** |
| 贴图实测 | `_MainTex`、`_BaseMap` 均 **2048×2048 DXT1,5.3 MB 各** |
| 贴图导入设置 | **`maxTextureSize = 2048`**、`textureType = Default`、mip = True |

**由此得到的两条结论**

1. **「不降采样」在导入侧今天不成立**:Unity 默认把 4096 源静默压到 2048(边长减半、像素 1/4),
   要保住 4096 必须显式改 `maxTextureSize` 或写导入预设。这是 §8.10.6.9 那条裁定
   **在引擎侧尚未兑现**的事实,不是解释。
2. **DCC 面数 ≠ 引擎顶点数**:同一件资产差 **38%**。以后报顶点数必须注明是哪一侧。

**成本换算**

| 项 | 单件 | 环境三件 |
|---|---|---|
| 网格 | 43.0 MB | ≈129 MB |
| 贴图(2048 实际) | 10.6 MB | ≈31.8 MB |
| **合计** | **≈53.6 MB** | **≈161 MB** |
| 若按 4096 导入 | ≈85 MB | ≈255 MB |

> 在 4 GB 显存上三件占 4% —— **不致命**,但**不随内容量缩放**:20 件同类道具即 ≈860 MB 网格。

**未测**:帧时间(Editor batch 不是游戏循环;本机 GTX 1050 Ti 也不是 P0 目标硬件)⇒ `NOT-RUN`。

**症状**:第一版交付件的 `check_fbx.py` 报 **边界边 22,258 / 23,056**,而非清理轮的 0 / 4。

**归因**:`decimate_glb.py` 导入 glb 后**直接**加 Decimate(COLLAPSE)修改器,而 glb 的顶点
按 UV 缝**已拆开**(清理轮合并掉 77,526 / 93,692 个重复点)。修改器看不到「缝两侧是同一个点」,
在每条缝两侧各自坍缩 ⇒ **网格沿 UV 缝裂开**。

**修法**:减面前插入 `bmesh.ops.remove_doubles(dist=1e-5)`(UV 存在 loop 上,按位置焊接不丢 UV)。

**修后实测**:断墙 20k 边界边 **0**(仍闭合);帐篷 20k 边界边 **15**(原件 4,新增 11 = 布面小孔级)。

**为什么这条必须写进来**:撕裂版**照样能过面数门**(门只数三角面),**照样能过构建**,
在 512 px 预览上也**看不出裂纹**。它只在一个没人会主动跑的判据上现形 ——
即「合并重复点后的边界边数」。**面数门不覆盖拓扑**,这一点不因本轮转绿而改变。

### 14.5 第三态(`asset_home: local-only`)—— 为什么要有它

**问题**:模型按策略不入库(ToS `⏸`),而 P6 是「声明的 asset 不存在 ⇒ 红」。
两者相撞的后果不是「少测一件」,是**任何没有这些二进制的机器上构建恒红** ——
门会把「按策略缺席」误报成「文件丢了」,红一次之后所有人都会去关掉它。

**改法**(用户 2026-11-12 裁定「不入库 + 门加第三态」):

| 状况 | 结果 |
|---|---|
| `asset_home` 缺省(`repo`)+ 文件不在 | **红**(P6 原样) |
| `asset_home: local-only` + 文件不在 | 记 `本地缺席`,告警「未测(不是通过)」,**不红** |
| `asset_home: local-only` + 文件在 | **照常量、照常红**(第三态不是免检通道) |
| `asset: pending` + `local-only` 同写 | **红**(两套「缺席」口径互斥) |
| `asset_home` 值拼错(如 `local_only`) | **红**(防止错字把「按策略缺席」静默降级成 `repo`) |

**如实登记**:这是我**自己加的设计**,不是用户逐条确认的。用户裁定的是「第三态」这个方向。
