## AC-21a-47:物品表全量加载 + 单次配方求解 < 1 ms

| 项 | 值 |
|---|---|
| **阈值** | < 1 ms(GDD 原文) |
| **方法** | 【桌面】菜单「大医精诚/数据管线/性能冒烟:AC-47 计时」一键出三数:全新 provider 首触 `Load<ItemDataSet>` 单发(首次装载);同 provider 1000 次 `Load` 中位(缓存命中);`RecipeSettlementSolver.Solve` 以首条配方 1000 次中位(单次求解)。前置:先「烘焙 item-database」+「确保 data-core Addressables 组」;要相对干净的「首次」就重启编辑器后先跑本菜单。结果进 Console + 剪贴板,回填下表 |

| **记录值** | **首次装载 = 70936 μs**(超阈 → 调优信号,判读见下);**缓存命中 = 0 μs**;**单次求解 = 0 μs** |

- **判读 ①(缓存 / 求解 ✓)**:`0 μs` 是整数微秒截断 —— `ticks×10⁶/Frequency = 0` ⇒ 本机 Stopwatch 分辨率下单次耗时 **< 1 μs**,远低于 1000 μs 阈值,两站稳过。
- **判读 ②(首次超阈 = 调优信号,非失败)**:70936 μs ≈ 70.9 ms 的主体是 **Addressables 子系统冷启动 + 编辑器 asset-database 装载路径**,不是表解码成本(表体 444 B / 4 条 ItemDef)。smoke 本就约定「超阈 = 调优信号」;待 Boot 启动序接线后(后续故事)可在运行期再取玩家构建口径的冷启动数。热会话下「provider 冷 + Addressables 热」的表本体首次可另测(与 E-13 干净会话同批,见 Edge)。
- **Edge:冷态互斥(旧机制下,已随机制改判作废)** —— 上一版「计时首次 / E-13 反向都要会话零预载」的互斥,是**改地址反向**机制下的判断:先跑计时会持有 `ItemsAddress` 活句柄(provider 不 Release),随后改地址仍命中缓存 ⇒ 反向不触发。**2026-09-24 两次实测(含按指引重启后单跑 E-13)确认根因不是这个 —— 是 `SetAddress(postEvent)` 根本不重建运行期 locator**(地址→GUID 映射在域初始化时按 settings 建好,之后菜单内改 address 不会同步刷新,**重启也不能解决**,因为陈旧发生在菜单内 SetAddress 与 Load 之间,与会话是否重启无关)。改地址方案已判定不可用,反向改走「文件暂移」机制(见下),不再依赖会话冷态,**本 Edge 就此作废**,保留作机制演进的失败记录。
- **E-13 失败路径(另测,不与计时混测)** —— 菜单「大医精诚/数据管线/E-13 自检(反路径+正复验)」:
